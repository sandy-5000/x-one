Docker Swarm deep dive — Apple IC4 preparation

Compose describes a multi-service application on one host. Swarm mode takes almost the same description and runs it across many hosts, with a control loop that keeps the cluster in the desired state.

Even if your team runs Kubernetes, Swarm is worth learning properly. It is a small, readable orchestrator, and almost every concept maps directly onto Kubernetes: desired state, reconciliation, scheduling, service discovery, rolling updates, and consensus.

By the end of this lesson you should be able to:

  • Explain how managers reach consensus and what happens when they lose quorum.
  • Trace a request through the routing mesh to a task on another node.
  • Run a zero-downtime rolling update and an automatic rollback.
  • Debug a task stuck in Pending or restarting in a loop.
  • Argue when Swarm is a reasonable choice and when it is not.

1. Swarm mode versus "classic Swarm"

  • Classic Swarm — a separate, now-retired product that pooled Docker hosts behind one API.
  • Swarm mode — built into Docker Engine since 1.12, based on the SwarmKit library. This is what docker swarm init enables, and what this lesson covers.

No extra software is needed: every Docker Engine can become a Swarm node.

2. Architecture

+------------------------------------------------------------------+
|                         Control plane                            |
|                                                                  |
|   +--------------+     +--------------+     +--------------+     |
|   |  manager-1   | <-> |  manager-2   | <-> |  manager-3   |     |
|   |   (leader)   |     |  (follower)  |     |  (follower)  |     |
|   +--------------+     +--------------+     +--------------+     |
|        Raft log: services, tasks, networks, secrets, nodes       |
+------------------------------------------------------------------+
                                 |
                       task assignments (gRPC)
                                 |
                                 v
+------------------------------------------------------------------+
|                           Data plane                             |
|                                                                  |
|   +--------------+     +--------------+     +--------------+     |
|   |   worker-1   |     |   worker-2   |     |   worker-3   |     |
|   | web.1  api.2 |     | api.1        |     | web.2  db.1  |     |
|   +--------------+     +--------------+     +--------------+     |
+------------------------------------------------------------------+

Managers

  • Store the cluster state in a Raft log, replicated to every manager.
  • Exactly one manager is the leader. Only the leader commits changes; followers forward writes to it.
  • Run the orchestrator (how many tasks should exist), the scheduler (which node runs each task), and the dispatcher (hands tasks to nodes).
  • Also run tasks by default. In production you often drain managers so they only do control-plane work.

Workers

  • Receive task assignments from managers and run them as containers.
  • Report task status back.
  • Do not participate in Raft and cannot change cluster state.

Services, tasks, and containers

Service "api"  (desired state: image=api:1.4, replicas=3)
   |
   +-- Task api.1  -->  container on worker-2
   +-- Task api.2  -->  container on worker-1
   +-- Task api.3  -->  container on worker-3
  • A service is the desired state you declare.
  • A task is one scheduled unit of that service — a slot assigned to a node. Tasks are immutable: to change one, Swarm shuts it down and creates a new one.
  • A container is what actually runs for the task.

When a node dies, its tasks are marked failed and the orchestrator creates new tasks on healthy nodes. That reconciliation loop is the core difference from Compose.

3. Raft and quorum

Every change — creating a service, scaling, adding a secret — must be committed by a majority of managers. That majority is the quorum.

+----------+--------+--------------------+
| Managers | Quorum | Failures tolerated |
+----------+--------+--------------------+
| 1        | 1      | 0                  |
| 2        | 2      | 0                  |
| 3        | 2      | 1                  |
| 4        | 3      | 1                  |
| 5        | 3      | 2                  |
| 7        | 4      | 3                  |
+----------+--------+--------------------+

Lessons from the table:

  • Use an odd number of managers. Going from 3 to 4 adds overhead without adding fault tolerance.
  • 3 or 5 managers is the normal range. More managers mean slower commits, because every write needs more acknowledgements.
  • 2 managers is worse than 1. Either failure loses quorum.
  • Spread managers across failure domains (racks, availability zones), or one outage takes out the majority.

What losing quorum means

  • Running tasks keep running. The data plane does not stop.
  • You cannot change anything: no deploys, no scaling, no rescheduling of failed tasks.
  • Recovery when the lost managers cannot come back: on a surviving manager, run docker swarm init --force-new-cluster. This creates a new single-manager cluster from the local state; then re-add managers.

4. Creating a cluster

# on the first manager
docker swarm init --advertise-addr 10.0.0.11

# print join commands
docker swarm join-token worker
docker swarm join-token manager

# on each other node
docker swarm join --token <token> 10.0.0.11:2377

# inspect
docker node ls
docker info --format '{{json .Swarm}}'

--advertise-addr matters on hosts with several interfaces: it is the address other nodes use to reach this one.

Required ports between nodes

+-----------+----------+-------------------------------------+
| Port      | Protocol | Purpose                             |
+-----------+----------+-------------------------------------+
| 2377      | TCP      | Cluster management (to managers)    |
| 7946      | TCP/UDP  | Node-to-node gossip and discovery   |
| 4789      | UDP      | Overlay network data (VXLAN)        |
| ESP (50)  | IP proto | Encrypted overlay traffic, if used  |
+-----------+----------+-------------------------------------+

A cluster that forms but whose cross-node service traffic silently fails is very often a blocked 4789/udp.

Token hygiene

  • Manager tokens grant full control of the cluster. Treat them like root credentials.
  • Rotate them with docker swarm join-token --rotate manager.

5. Services

docker service create \
  --name api \
  --replicas 3 \
  --publish published=8080,target=3000 \
  --network backend \
  --health-cmd "wget -qO- http://localhost:3000/health || exit 1" \
  --health-interval 10s \
  --limit-memory 512M \
  --reserve-memory 256M \
  myorg/api:1.4

docker service ls
docker service ps api
docker service inspect --pretty api
docker service logs -f api
docker service scale api=5

Replicated versus global

  • Replicated (default) — run exactly N tasks, wherever the scheduler places them.
  • Global — run one task on every eligible node. Use it for node-level agents: log shippers, metrics exporters, security scanners.
docker service create --mode global --name node-exporter prom/node-exporter

Reservations versus limits

  • --reserve-memory / --reserve-cpu — used by the scheduler. A node is only eligible if it has that much unreserved capacity.
  • --limit-memory / --limit-cpu — enforced by cgroups at runtime. Exceeding the memory limit gets the container OOM-killed.

Setting limits without reservations lets the scheduler overpack nodes. Setting reservations without limits lets one task starve its neighbours.

6. Networking

Overlay networks

An overlay network spans every node that runs a task attached to it. Traffic between nodes is encapsulated in VXLAN over UDP 4789.

docker network create --driver overlay --attachable backend
docker network create --driver overlay --opt encrypted secure-backend
  • --attachable lets standalone containers (docker run --network backend) join, which is handy for debugging.
  • --opt encrypted adds IPsec encryption between nodes, at some CPU cost.

Service discovery: VIP versus DNS round-robin

By default each service gets a virtual IP (VIP). The service name resolves to that single VIP, and the kernel's IPVS load-balances connections across healthy tasks.

api  --> DNS -->  10.0.1.5 (VIP)  --> IPVS --> api.1 / api.2 / api.3

With --endpoint-mode dnsrr, the name resolves directly to all task IPs and the client chooses. Use it when a client needs to see individual instances, or with protocols that do not work through the VIP.

tasks.api always resolves to the individual task IPs, whichever mode is set.

The routing mesh

Publishing a port in the default ingress mode opens it on every node, even nodes that run no task of that service.

                client  -->  any node : 8080
                                  |
            +---------------------+---------------------+
            |                     |                     |
      +-----------+         +-----------+         +-----------+
      |  node-1   |         |  node-2   |         |  node-3   |
      |  api.1    |         |  (none)   |         |  api.2    |
      +-----------+         +-----------+         +-----------+
            ^                     |
            +----- ingress network forwards to a healthy task
  • An external load balancer can target all nodes without knowing where tasks run.
  • The cost is an extra network hop, and the client's source IP is replaced by an internal address.

When you need the real client IP or lower latency, publish in host mode:

docker service create --mode global \
  --publish published=443,target=443,mode=host \
  --name edge-proxy traefik:v3

Host mode binds only on nodes that run a task, so it is usually combined with --mode global.

7. Rolling updates and rollbacks

docker service update \
  --image myorg/api:1.5 \
  --update-parallelism 1 \
  --update-delay 10s \
  --update-order start-first \
  --update-failure-action rollback \
  --update-monitor 30s \
  --update-max-failure-ratio 0.1 \
  api

What each setting does:

  • --update-parallelism — how many tasks are replaced at a time.
  • --update-delay — wait between batches.
  • --update-order — stop-first (default) stops the old task before starting the new one; start-first starts the new one first, giving zero-downtime replacement at the cost of briefly running extra tasks.
  • --update-monitor — how long to watch each new task for failure after it starts.
  • --update-failure-action — pause (default), continue, or rollback.
  • --update-max-failure-ratio — the fraction of failed tasks tolerated before the failure action fires.

Health checks make updates safe

Without a health check, a task counts as "running" as soon as its process starts — even if the application immediately fails its first request. With a health check, Swarm waits for healthy before counting the task as updated and moving to the next batch.

Manual rollback

docker service rollback api
docker service inspect --format '{{json .PreviousSpec}}' api

Swarm keeps exactly one previous spec, so a rollback goes back one step only.

8. Scheduling and placement

Constraints — hard rules

docker node update --label-add zone=az1 worker-1
docker node update --label-add disk=ssd worker-2

docker service create \
  --constraint 'node.role==worker' \
  --constraint 'node.labels.disk==ssd' \
  --name db postgres:16

A task with constraints that no node satisfies stays Pending forever. It does not fail.

Preferences — soft spreading

docker service create --replicas 6 \
  --placement-pref 'spread=node.labels.zone' \
  --name api myorg/api:1.4

This spreads tasks evenly across zones, so losing one zone removes only a share of the capacity.

Node availability

  • active — accepts new tasks.
  • pause — keeps existing tasks, accepts no new ones.
  • drain — moves all tasks off the node. Use it before maintenance.
docker node update --availability drain worker-2
# patch and reboot worker-2
docker node update --availability active worker-2

Swarm does not automatically rebalance existing tasks back onto a node that returns. New tasks go there; to rebalance now, run docker service update --force api.

9. Secrets and configs

printf 's3cr3t' | docker secret create db_password_v1 -
docker service create --secret source=db_password_v1,target=db_password --name api myorg/api:1.4
  • Secrets are stored encrypted in the Raft log.
  • They are only sent to nodes that run a task needing them.
  • Inside the container they appear as files in an in-memory filesystem at /run/secrets/<target>. They never touch the node's disk.

Secrets are immutable. To rotate one:

printf 'n3w-s3cr3t' | docker secret create db_password_v2 -
docker service update \
  --secret-rm db_password_v1 \
  --secret-add source=db_password_v2,target=db_password \
  api
docker secret rm db_password_v1

Because the target stays the same, the application does not change; the update rolls out like any other.

Configs (docker config create) work the same way for non-sensitive files such as an nginx.conf.

Autolock

By default, the keys that decrypt the Raft log are stored on each manager's disk. With autolock, a restarted manager stays locked until an operator supplies an unlock key:

docker swarm update --autolock=true
docker swarm unlock
docker swarm unlock-key

Store the unlock key outside the cluster. Losing it while managers are locked means rebuilding the cluster.

10. Stacks: Compose files on a cluster

A stack deploys a Compose file to the Swarm:

services:
  api:
    image: registry.example.com/api:1.5
    networks: [backend]
    secrets: [db_password]
    deploy:
      replicas: 3
      update_config:
        parallelism: 1
        delay: 10s
        order: start-first
        failure_action: rollback
      restart_policy:
        condition: on-failure
        max_attempts: 3
      resources:
        limits:
          memory: 512M
        reservations:
          memory: 256M
      placement:
        constraints: [node.role == worker]

networks:
  backend:
    driver: overlay

secrets:
  db_password:
    external: true
docker stack deploy -c stack.yaml --with-registry-auth shop
docker stack services shop
docker stack ps shop
docker stack rm shop

Differences from plain Compose

  • build: is ignored. Every node must be able to pull the image from a registry, so build and push in CI first.
  • depends_on is ignored. Services start in any order, so retries in the application are mandatory.
  • container_name is not allowed: tasks are named by Swarm.
  • --with-registry-auth forwards your registry credentials to the nodes so they can pull private images.
  • Re-running stack deploy is the update mechanism. It is declarative: services removed from the file are only cleaned up with --prune.

Pin images by digest

If a stack references api:latest, different nodes may resolve the tag at different times and run different code. Pin a version tag, or better, a digest: api@sha256:....

11. Operations

Back up the Raft state

The cluster state lives in /var/lib/docker/swarm on each manager.

  1. Stop Docker on one manager (in a 3- or 5-manager cluster, quorum survives).
  2. Archive /var/lib/docker/swarm.
  3. Start Docker again.

If autolock is on, you also need the unlock key to restore the backup.

Upgrading the cluster

  • Upgrade managers one at a time, checking that quorum and leadership are healthy between each.
  • Drain each worker, upgrade it, and reactivate it.

Observability

  • docker service logs aggregates logs across nodes but is not a log platform. Ship logs to a central system with a global logging agent.
  • Run node and container exporters as global services, and alert on task restarts, pending tasks, and manager reachability.

12. Debugging playbook

Scenario A — a task stays in Pending

docker service ps --no-trunc api

Look at the ERROR column. Common causes:

  • no suitable node — constraints or labels that no node satisfies.
  • insufficient resources — reservations larger than any node's free capacity.
  • The image cannot be pulled on that node. Check registry auth and --with-registry-auth.

Scenario B — tasks restart in a loop

  • docker service ps api shows a history of failed tasks with exit codes.
  • Exit code 137 usually means OOM-killed or SIGKILL — compare memory usage to the limit.
  • A failing health check kills the task even if the process is alive. Run the check command manually inside a container to see why.

Scenario C — service works on one node but not across nodes

  • Check that 4789/udp and 7946 are open between nodes.
  • Check for MTU problems: VXLAN adds about 50 bytes of overhead, so large packets can be dropped silently on networks with a small MTU.
  • Use an attachable overlay and a debug container to test tasks.api resolution and connectivity.

Scenario D — a rolling update pauses halfway

docker service inspect --format '{{json .UpdateStatus}}' api

The default failure action is pause. Fix the cause, then either docker service update api to resume or docker service rollback api.

13. Hands-on labs

You can practise most of this on one machine with a single-node swarm, and multi-node behaviour with three small VMs (for example, using Multipass).

Lab A — Reconciliation

docker swarm init
docker service create --name web --replicas 3 -p 8080:80 nginx:alpine
docker ps --filter name=web
docker rm -f $(docker ps -q --filter name=web | head -1)
docker service ps web

Watch Swarm replace the container you killed.

Lab B — Rolling update with automatic rollback

Deploy a service with a health check, then update it to an image whose health check fails. Use --update-failure-action rollback and observe the automatic rollback in docker service ps.

Lab C — VIP versus DNS round-robin

docker network create -d overlay --attachable lab
docker service create --name whoami --replicas 3 --network lab traefik/whoami
docker run --rm --network lab alpine sh -c "nslookup whoami; nslookup tasks.whoami"

Lab D — Losing quorum

On a three-manager cluster, stop Docker on two managers. Confirm that existing tasks keep running but docker service scale fails. Restore one manager and confirm writes work again.

14. Swarm versus Kubernetes

+---------------------+---------------------------+-----------------------------+
| Concern             | Swarm                     | Kubernetes                  |
+---------------------+---------------------------+-----------------------------+
| Setup               | Built into Docker Engine  | Separate control plane      |
| Config format       | Compose file              | Many resource types (YAML)  |
| State store         | Raft inside managers      | etcd                        |
| Unit of scheduling  | Task (one container)      | Pod (one or more)           |
| Service discovery   | VIP + DNS, routing mesh   | Service + kube-proxy, DNS   |
| Autoscaling         | Not built in              | HPA, VPA, cluster autoscale |
| Ecosystem           | Small                     | Very large                  |
+---------------------+---------------------------+-----------------------------+

When Swarm is reasonable

  • Small teams that already know Compose and need a few nodes with failover.
  • Edge or on-premise sites where a full Kubernetes distribution is too heavy.

When to choose Kubernetes

  • You need autoscaling, rich deployment strategies, custom controllers, or a large ecosystem of operators.
  • The organisation already runs Kubernetes, which at most large companies it does.

Knowing Swarm well makes Kubernetes easier, because you already understand the problems it solves.

15. Interview questions with model answers

What happens to running containers if a Swarm loses quorum?

They keep running. Only the control plane is affected: no deploys, no scaling, and failed tasks are not rescheduled until quorum is restored or the cluster is force-rebuilt from a surviving manager.

Why run 3 managers rather than 4?

Both tolerate exactly one manager failure, because quorum for 4 is 3. The fourth manager adds replication overhead without adding fault tolerance.

How does a request reach a task on another node?

With ingress publishing, every node listens on the published port. IPVS on the receiving node load-balances the connection to a healthy task's IP on the ingress overlay network, and VXLAN carries it to the node running that task.

How do you rotate a secret without downtime?

Create a new secret with a new name, update the service to remove the old one and add the new one with the same target path, let the rolling update replace tasks, then delete the old secret.

Why does depends_on not help in a stack?

docker stack deploy ignores it. Services start in any order and can restart independently at any time, so each service must retry its dependencies.

A task is stuck in Pending. What do you check?

docker service ps --no-trunc for the scheduler's error, then constraints and node labels, resource reservations versus free capacity, node availability, and whether the image can be pulled on candidate nodes.
