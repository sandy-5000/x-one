3. Start with the fundamentals: Day 1

Do not begin by memorizing Docker commands. Start by understanding what problem containers solve.

3.1 Virtual machines versus containers

Virtual machine

Each VM runs a guest operating system on virtualized hardware. A hypervisor isolates the VMs.

Container

Processes share the host kernel while namespaces, cgroups, filesystem configuration, and security controls provide isolation.

The critical distinction is that a normal Linux container is not a virtual machine. It does not boot its own independent Linux kernel. The isolation is implemented largely through facilities provided by the host kernel.

This explains several important properties:

  • Containers typically start faster than full VMs because they do not boot a separate guest OS.
  • Multiple containers can share the same host kernel.
  • A container's resource usage still consumes host resources.
  • A Linux container on macOS generally runs inside a Linux VM because macOS does not provide the Linux kernel interfaces that Linux containers require.

3.2 The five concepts you must understand first

Namespaces — isolation

Control what a process can see: process IDs, network interfaces, mount points, hostnames, IPC objects, users, and cgroup views.

Cgroups — resource accounting and control

Track and constrain resources such as CPU and memory. Memory limits can lead to OOM kills; CPU limits can cause throttling.

Filesystem isolation

Mount namespaces and a configured root filesystem give a process its own filesystem view. Image layers and OverlayFS help construct that view.

Capabilities and syscall restrictions

Linux capabilities divide up privileged operations; seccomp can restrict system calls. Neither should be confused with complete isolation on its own.

Processes and signals

A container normally runs an ordinary Linux process. Its lifecycle depends on the configured entrypoint, process exit status, signal handling, and runtime behavior.

2. The foundation: a container is an isolated process environment

A container is not inherently a small virtual machine. On Linux, it is a collection of ordinary processes configured with isolation and resource controls.

The kernel provides the fundamental mechanisms. A container runtime configures them, prepares a root filesystem, applies security restrictions, and starts the process.

Virtual machine versus container

Virtual machine architecture

Physical hardware

Hypervisor

VM A

Guest OS + libraries

Application A

VM B

Guest OS + libraries

Application B

Linux container architecture

Physical hardware

One shared Linux kernel

Container A

Namespaces + rootfs

Application A

Container B

Namespaces + rootfs

Application B

The important distinction:

  • A VM generally has its own guest kernel.
  • A normal Linux container uses the host's Linux kernel.
  • Containers can have different filesystem views, network stacks, process ID views, and resource limits.
  • Containers are not equivalent to security boundaries as strong as a correctly configured, hardware-virtualized VM in every threat model.

Apple interview angle: If asked why containers are lightweight, do not just say they share the kernel. Explain that they avoid booting a separate guest OS and can reuse image layers, while isolation is largely configured through existing kernel mechanisms.

3. Linux namespaces: controlling what a process can see

Namespaces isolate particular views of system resources. A process can live in several namespaces simultaneously.

+-----------+--------------------------------------------------------------------+
| Namespace | What it isolates                                                   |
+-----------+--------------------------------------------------------------------+
| `pid`     | Process ID hierarchy and process visibility                        |
| `net`     | Network devices, routes, sockets, and network stack                |
| `mnt`     | Mount table and filesystem mount visibility                        |
| `uts`     | Hostname and domain name                                           |
| `ipc`     | System V IPC and POSIX message queues                              |
| `user`    | User and group ID mappings and associated privilege interpretation |
| `cgroup`  | View of the cgroup hierarchy                                       |
| `time`    | Certain system and boot-time clock views                           |
+-----------+--------------------------------------------------------------------+

A key nuance: namespaces isolate views, not necessarily every underlying resource or all access to it. For example, a network namespace isolates network configuration, but firewall rules, host access, and capabilities still affect security.

Example: two different PID views

Suppose the host is running these processes:

+------------------------------+
|      Host PID namespace      |
+------------------------------+
                |
                v
+------------------------------+
|      ├ PID 1   systemd       |
+------------------------------+
                |
                v
+------------------------------+
|   ├ PID 800 docker daemon    |
+------------------------------+
                |
                v
+------------------------------+
| ├ PID 1400 container runtime |
+------------------------------+
                |
                v
+------------------------------+
| PID 2500 application process |
+------------------------------+

Inside the container's PID namespace, the same application process might appear as PID 1:

+-------------------------+
| Container PID namespace |
+-------------------------+
             |
             v
+-------------------------+
|   PID 1   application   |
+-------------------------+

The application is not two different processes. It has one identity in the underlying process hierarchy, but its PID can be represented differently in nested PID namespaces.

This is one reason ps inside a container and ps on the host can show different results.

Hands-on lab 1: inspect namespace IDs

Run:

lsns

Then inspect your current shell:

readlink /proc/self/ns/pid
readlink /proc/self/ns/net
readlink /proc/self/ns/mnt
readlink /proc/self/ns/user

Example output will look like:

pid:[4026531836]
net:[4026531840]
mnt:[4026531841]
user:[4026531837]

These numeric identifiers are examples, not expected values for your machine. Linux exposes namespace references through /proc.

Now compare the namespace identifiers of two processes:

readlink /proc/1/ns/pid
readlink /proc/self/ns/pid

If both point to the same namespace, those processes share that PID namespace. If they differ, they belong to different PID namespaces.

Expected observation: Namespace identifiers are kernel-managed identifiers, not Docker container IDs.

4. Cgroups: controlling how much a process can consume

Namespaces answer: What can the process see?

Control groups, or cgroups, answer: How are resources accounted for and constrained?

For example, a container can have a memory limit of 128 MiB. If its workload exceeds what the kernel can sustain under that limit, the kernel's memory-control mechanisms may trigger an OOM kill.

Cgroups can also control CPU bandwidth, track memory usage, and manage I/O resources, depending on the controller and configuration.

Inspect cgroups on your machine

Run:

cat /proc/self/cgroup

On a cgroups v2 system, you may see:

0::/user.slice/user-1000.slice/session-2.scope

The exact path depends on your machine and session.

Check the cgroup filesystem:

mount | grep cgroup

Check whether your system uses cgroups v2:

stat -fc %T /sys/fs/cgroup

Output of cgroup2fs indicates a cgroups v2 filesystem at that path.

If readable, inspect available controllers:

cat /sys/fs/cgroup/cgroup.controllers

You may see controllers such as cpu, memory, and io.

Understand the CPU limit

Suppose a container is configured with:

docker run --rm --cpus=0.5 alpine sleep 60

The CPU limit restricts the container to approximately half a CPU's worth of sustained execution capacity under the relevant cgroup CPU quota configuration. It does not mean the process is permanently assigned half of a physical core.

For a busy process, the kernel may throttle execution after it consumes its allotted CPU time during a scheduling period.

This is important in production because high latency can occur even when the host has spare CPU capacity: a particular container may be constrained by its own quota.

Namespace versus cgroup: interview comparison

+------------------------+-----------------------------+------------------------------------------------------+
| Property               | Namespace                   | Cgroup                                               |
+------------------------+-----------------------------+------------------------------------------------------+
| Primary purpose        | Isolation of resource views | Resource accounting and control                      |
| Example                | Separate network interfaces | CPU quota                                            |
| Another example        | Separate PID view           | Memory limit                                         |
| Typical debugging tool | `lsns`, `/proc/PID/ns`      | `cat /proc/PID/cgroup`, cgroup files, `docker stats` |
+------------------------+-----------------------------+------------------------------------------------------+

They are complementary, not interchangeable.

5. Filesystem isolation: why / looks different inside a container

A Linux process resolves paths relative to its root directory. A container runtime can construct a filesystem tree containing the application's executable, shared libraries, configuration files, and other required files, then arrange for the process to use that tree as its root filesystem.

Consider this layout:

+-----------------+
| Host filesystem |
+-----------------+
         |
         v
+-----------------+
|        /        |
+-----------------+
         |
         v
+-----------------+
|      ├ etc/     |
+-----------------+
         |
         v
+-----------------+
|     ├ home/     |
+-----------------+
         |
         v
+-----------------+
|      ├ usr/     |
+-----------------+
         |
         v
+-----------------+
|      ├ var/     |
+-----------------+
         |
         v
+-----------------+
| var/lib/docker/ |
+-----------------+
         |
         v
+-----------------+
|       ...       |
+-----------------+

A container might instead see:

+---------------------------+
| Container root filesystem |
+---------------------------+
              |
              v
+---------------------------+
|             /             |
+---------------------------+
              |
              v
+---------------------------+
|           ├ bin/          |
+---------------------------+
              |
              v
+---------------------------+
|           ├ etc/          |
+---------------------------+
              |
              v
+---------------------------+
|           ├ lib/          |
+---------------------------+
              |
              v
+---------------------------+
|           ├ tmp/          |
+---------------------------+
              |
              v
+---------------------------+
|            app/           |
+---------------------------+
              |
              v
+---------------------------+
|           server          |
+---------------------------+

The host's filesystem still exists. The container sees a configured filesystem view.

Three concepts are worth distinguishing:

  • Mount namespace: isolates the mount table.
  • Root filesystem: the filesystem tree exposed as / to the process.
  • OverlayFS: can combine lower, read-only filesystem layers with a writable upper layer.

chroot changes a process's apparent root directory but does not, by itself, provide complete container isolation or a strong security boundary.

6. What actually happens during docker run?

Consider:

docker run --rm -p 8080:80 nginx

At a high level, the flow is:

Docker CLI

Parses the command and calls the Docker API

Docker daemon (dockerd)

Coordinates image, container, network, and storage operations

containerd

Manages container lifecycle and runtime tasks

OCI runtime, commonly runc

Sets up the container environment and starts the process

Linux kernel + application process

Kernel enforces configured isolation and resource controls

This is a simplified architecture. Exact responsibilities and call paths vary by Docker version, runtime configuration, and platform. The CLI generally communicates through the Docker API; dockerd commonly delegates container lifecycle work to containerd, which invokes an OCI runtime to create and start a container process.

The command involves several operations:

  1. Resolve the requested image locally or pull it from a registry.
  2. Prepare the container's root filesystem and writable layer.
  3. Configure namespaces, cgroups, capabilities, and security settings.
  4. Configure networking and publish host port 8080 to container port 80.
  5. Start the configured application process.
  6. Track the container's lifecycle and exit status.

The kernel does not know that the process is an "Nginx Docker container" in the same sense that Docker does. The runtime and supporting infrastructure manage that higher-level concept using kernel facilities and metadata.

Hands-on lab 3: observe the lifecycle

Run:

docker run -d --name nginx-lab -p 8080:80 nginx

Then:

docker ps
docker inspect nginx-lab
docker logs nginx-lab
curl -I http://localhost:8080

Observe the running container's host process:

docker top nginx-lab

Finally:

docker stop nginx-lab
docker ps -a
docker rm nginx-lab

Answer these questions:

  • Which process is the container's main process?
  • Why does the container stop when its main process exits?
  • Why does docker stop behave differently from abruptly killing a process?
  • What is the difference between stopping and removing a container?
  • What changes if you remove -p 8080:80?

Do not assume that every container uses the same PID 1 process or has identical signal-handling behavior.

7. Debugging exercises: think like a production engineer

For each scenario, form a hypothesis, inspect evidence, and only then change configuration.

Scenario A — The container exits immediately

You execute:

docker run -d --name test alpine

The container exits.

Why? The image's default command may finish immediately. A container is not required to keep running when its work is done.

Inspect it:

docker ps -a
docker inspect test --format '{{.State.Status}} {{.State.ExitCode}}'
docker logs test
docker rm test

Compare with:

docker run -d --name test alpine sleep 600

The second command keeps a process alive for ten minutes.

IC4 takeaway: Containers are process-oriented. A container being stopped does not automatically mean Docker failed.

Scenario B — The application works inside the container but cannot be reached from the host

Start a web server without publishing its port:

docker run -d --name web nginx

Inspect the port configuration:

docker port web
docker inspect web --format '{{json .NetworkSettings.Ports}}'

Compare it with:

docker rm -f web
docker run -d --name web -p 8080:80 nginx
curl -I http://localhost:8080

The first container does not have a host port published by the command. The second explicitly requests host-to-container port publishing.

IC4 takeaway: A listening socket inside a container and a reachable service on the host are two different conditions. Networking configuration must connect them.

Scenario C — The container is slow despite low host CPU usage

Investigate:

docker stats
docker inspect <container_name>

Then examine cgroup CPU statistics on the host, where accessible:

cat /proc/<host_pid>/cgroup

For cgroups v2, inspect the relevant cgroup's cpu.stat and cpu.max files. The cgroup path must be resolved from the process's membership and the host's cgroup mount.

Look for:

  • CPU quota limits.
  • Increasing throttling counters.
  • Memory pressure and reclaim activity.
  • Excessive disk I/O or application-level contention.

IC4 takeaway: Low overall host CPU utilization does not prove that a container is unconstrained. Diagnose the resource limit and the workload, not just the host's aggregate metrics.

Scenario D — The container runs as root

Inspect:

docker exec <container_name> id

Running as root inside a container does not necessarily grant unrestricted root privileges on the host. However, the risk depends on user namespaces, capabilities, mounts, runtime configuration, and kernel vulnerabilities.

For an application that does not need elevated privileges, use a non-root user and remove unnecessary capabilities. Consider a read-only root filesystem where appropriate.

IC4 takeaway: Container isolation is layered defense, not a substitute for least privilege.

8. Apple IC4 interview questions with model answers

Use the answers below as a baseline. Practice explaining the mechanism in your own words rather than memorizing the wording.

Q1. What is a container, internally?

A container is a process or group of processes running with an isolated environment configured by a runtime. On Linux, that environment typically uses namespaces for isolation, cgroups for resource control, a prepared root filesystem, and security controls such as capabilities and seccomp. The processes share the host kernel.

Q2. Are namespaces sufficient to implement a container?

No. Namespaces isolate views of resources, but do not independently provide a filesystem, resource limits, or complete security. A runtime typically combines namespaces with a root filesystem, cgroups, capabilities, syscall restrictions, and other configuration.

Q3. How does a container get its own PID 1?

The runtime can create a PID namespace and start the container's initial process within it. That process can appear as PID 1 in the new namespace while having a different PID in an ancestor namespace. PID 1 has special signal-handling and orphan-reaping implications.

Q4. What happens when a container's PID 1 exits?

The container's main workload has exited, so the runtime normally considers the container stopped. Other processes in its PID namespace are terminated as part of PID namespace teardown. Restart policies or an orchestrator may subsequently start a replacement.

Q5. How are CPU and memory limits enforced?

On Linux, cgroups provide resource accounting and control. CPU bandwidth limits commonly use the CPU controller's quota configuration; memory limits use the memory controller. Under pressure, the workload can be throttled or encounter allocation failures and OOM termination.

Q6. Why can a container be less isolated than a VM?

Linux containers share a kernel, so a kernel vulnerability may affect the host and other containers. A VM adds a hardware-virtualization boundary and a separate guest kernel. The actual security difference depends on configuration, threat model, hypervisor, runtime, and available defenses.

Q7. Explain docker run from CLI to process creation.

The CLI sends a request through the Docker API. The daemon coordinates image, filesystem, network, and container setup, commonly delegating lifecycle management to containerd. An OCI runtime such as runc sets up the configured execution environment and starts the process, with the Linux kernel enforcing the relevant isolation and resource controls.

Q8. Why is chroot not equivalent to a container?

chroot changes a process's apparent root directory but does not by itself isolate PIDs, networking, mounts, resources, or privileges. It is not a complete security boundary.

Q9. What is the difference between an image and a container?

An image is an immutable template composed of filesystem content and configuration metadata. A container is a runtime instance created from an image, with its own lifecycle, execution configuration, and potentially a writable filesystem layer.

Q10. A container is killed with exit code 137. What do you investigate?

Exit code 137 conventionally indicates termination by signal 9 (SIGKILL) in common shell and container reporting contexts. It does not prove an OOM kill. Check container state and OOM indicators, kernel logs where permitted, cgroup memory events, orchestration events, and whether an operator or runtime forcibly killed the process.

Lesson 1 — Linux and container fundamentals

1.1 Processes, VMs, and containers

A process is a running program with state maintained by the operating system: memory mappings, file descriptors, credentials, scheduling information, and more.

A virtual machine typically runs a separate guest operating system and kernel. A Linux container ordinarily runs processes using the host's Linux kernel.

Containers are generally lighter because they do not boot a separate guest kernel. They are not automatically as strongly isolated as VMs in every security scenario.

1.2 The kernel mechanisms

+---------------------+------------------------------------------------------------------------+
| Mechanism           | Responsibility                                                         |
+---------------------+------------------------------------------------------------------------+
| Namespaces          | Isolate views of system resources                                      |
| Cgroups             | Account for and control resource usage                                 |
| Mount configuration | Build the container's filesystem view                                  |
| Capabilities        | Divide privileged operations into smaller permissions                  |
| Seccomp             | Restrict permitted system calls                                        |
| LSMs                | Apply security policies through mechanisms such as AppArmor or SELinux |

Namespaces and cgroups solve different problems.

Namespaces include PID, network, mount, UTS, IPC, user, cgroup, and time namespaces.

Lesson 2 — Docker Engine internals

2.1 Architecture

Docker is not one executable that directly implements every container operation. It has client, daemon, image, networking, storage, and runtime components.

Docker CLI

docker run, docker build, docker inspect

Docker API and daemon (dockerd)

containerd

Container lifecycle and tasks

OCI runtime, commonly runc

Configures and starts the container process

Linux kernel

This is a simplified common architecture; exact call paths depend on versions and runtime configuration.

  • Docker CLI: sends requests through the Docker API.
  • dockerd: coordinates Docker's higher-level operations.
  • containerd: manages container lifecycle and execution tasks.
  • runc: implements the OCI runtime interface for creating and starting containers.
  • OCI: defines interoperable specifications for container images and runtime bundles.

The kernel ultimately enforces process isolation, scheduling, memory management, networking, and filesystem operations.

2.2 Trace docker run

docker run --rm -p 8080:80 nginx

Typical stages:

  1. Resolve the image and pull it if needed.
  2. Prepare the root filesystem.
  3. Configure isolation, resource controls, and security.
  4. Configure the network and host port publishing.
  5. Start the application process.
  6. Track its lifecycle and exit status.
  7. Remove the container when it exits because --rm was specified.

Lab

docker version
docker info
docker run -d --name nginx-lab -p 8080:80 nginx
docker inspect nginx-lab
docker top nginx-lab
docker logs nginx-lab
curl -I http://localhost:8080
docker stop nginx-lab
docker rm nginx-lab

Interview questions

What is the difference between containerd and runc?

containerd manages higher-level container lifecycle and execution tasks. runc is an OCI runtime commonly invoked to create and start an individual container process environment.

Does Docker itself implement namespaces?

Docker orchestrates their configuration through the runtime and Linux kernel interfaces; the kernel implements the underlying namespace mechanisms.

What happens if the Docker CLI exits?

The daemon-managed container normally continues running. The CLI is a client, not the process supervising the container's entire lifetime.

Reference: Docker Engine, OCI Runtime Specification.

Lesson 3 — Images, layers, and registries

3.1 Image versus container

An image is a reusable template. A container is a runtime instance of that template.

Images commonly consist of filesystem layers, configuration metadata, and a manifest that describes their contents.

Illustrative image layers

Application layer

Application binary and files

Dependencies layer

Libraries and runtime

Base filesystem

Distribution files

Layers are content-addressed and can be reused across images when their content matches.

Important concepts:

  • Layer: filesystem changes represented as part of an image.
  • Manifest: describes an image's configuration and layers.
  • Digest: cryptographic content identifier, commonly SHA-256.
  • Tag: human-readable reference that can be moved to point to different image content.
  • Registry: stores and distributes images.
  • Writable layer: captures runtime filesystem changes separately from the underlying image layers in common storage configurations.

A tag such as nginx:latest is not immutable. A digest identifies specific content.

3.2 Commands to master

docker pull alpine
docker image ls
docker image inspect alpine
docker history alpine
docker image inspect alpine --format '{{json .RootFS.Layers}}'
docker image save alpine -o alpine.tar
docker image load -i alpine.tar

For registry operations:

docker login
docker tag myapp:latest registry.example.com/team/myapp:v1
docker push registry.example.com/team/myapp:v1

The registry URL and credentials must be replaced with real values for your environment.

3.3 Image distribution

At a high level:

  1. The client resolves a tag or digest to an image manifest.
  2. The registry returns manifest metadata.
  3. The client downloads required configuration and layers.
  4. Content is verified against the relevant digests.
  5. The engine stores image content and makes it available for container creation.

Modern registries can use different manifest formats and multi-platform indexes.

Interview questions

Why are image layers useful?

They permit reuse of common content, reduce repeated downloads, and enable build caching. Poor layer ordering can invalidate expensive downstream work.

Why deploy by digest?

A digest identifies exact image content, reducing ambiguity caused by mutable tags. For stronger supply-chain guarantees, also verify signatures, provenance, and policy.

Does deleting a container delete its image?

No. Container lifecycle and image lifecycle are separate. Image cleanup is a separate operation, and content can be shared with other images.

Reference: Docker image documentation.

Lesson 4 — Dockerfile, BuildKit, and efficient builds

4.1 Dockerfile instructions

+--------------+-----------------------------------------------------------------------+
| Instruction  | Purpose                                                               |
+--------------+-----------------------------------------------------------------------+
| `FROM`       | Selects the base image                                                |
| `WORKDIR`    | Sets the working directory                                            |
| `COPY`       | Copies build-context files                                            |
| `RUN`        | Executes a command during image construction                          |
| `ENV`        | Sets environment defaults                                             |
| `ARG`        | Defines build-time arguments                                          |
| `USER`       | Sets the user for subsequent operations and default runtime execution |
| `EXPOSE`     | Documents an intended listening port                                  |
| `ENTRYPOINT` | Defines the executable                                                |
| `CMD`        | Supplies default command or arguments                                 |
+--------------+-----------------------------------------------------------------------+

EXPOSE does not publish a host port. RUN executes during the build, whereas CMD defines a default command or arguments for container execution.

4.2 Build a Node.js application

Example:

FROM node:22-bookworm-slim AS build

WORKDIR /app
COPY package*.json ./
RUN npm ci

COPY . .
RUN npm run build

FROM node:22-bookworm-slim AS runtime

ENV NODE_ENV=production
WORKDIR /app

COPY package*.json ./
RUN npm ci --omit=dev && npm cache clean --force

COPY --from=build /app/dist ./dist

USER node
EXPOSE 3000
CMD ["node", "dist/server.js"]

This is illustrative. It assumes the project has a package-lock.json, a build script, a dist/server.js output, and no additional runtime assets or native dependencies requiring special handling.

A production implementation should also account for signal handling, dependency reproducibility, image provenance, health checks, and a suitable base-image patching policy.

Create .dockerignore:

node_modules
.git
.env
coverage
dist

Adjust it if dist is required from the host rather than generated during the build.

4.3 Build cache

BuildKit represents builds as a dependency graph and can parallelize independent work. Build cache reuse depends on the relevant inputs and instruction semantics.

A common optimization is:

COPY package*.json ./
RUN npm ci
COPY . .

This allows dependency installation to remain cached when only application source files change, provided the relevant dependency inputs remain unchanged.

Compare with:

COPY . .
RUN npm ci

Here, unrelated source changes can invalidate the dependency-installation step.

Build and inspect

docker build -t myapp:dev .
docker image history myapp:dev
docker build --no-cache -t myapp:clean .

Lesson 5 — Container lifecycle, PID 1, and signals

5.1 Lifecycle

A typical container progresses through states such as created, running, and stopped. Docker also reports restarting, paused, and other states depending on the situation.

docker create --name lifecycle alpine sleep 300
docker start lifecycle
docker inspect lifecycle --format '{{.State.Status}}'
docker stop lifecycle
docker inspect lifecycle --format '{{.State.Status}} {{.State.ExitCode}}'
docker rm lifecycle

A container can stop because its main process exits, fails, is killed, or encounters an execution error.

5.2 PID 1

The initial process in a PID namespace has special responsibilities:

  • It is the namespace's initial process.
  • It can adopt orphaned processes.
  • It has special signal semantics.
  • Its exit triggers termination of the remaining processes in that PID namespace.

Applications should handle termination signals correctly. Shell wrappers that do not use exec can interfere with signal delivery to the actual application.

Prefer:

CMD ["node", "dist/server.js"]

When a shell wrapper is required:

#!/bin/sh
set -eu

# Initialization steps
exec "$@"

The exec replaces the shell process with the application.

5.3 Stop versus kill

  • docker stop normally sends the configured stop signal, waits for a grace period, then sends SIGKILL if the process remains.
  • docker kill sends a signal immediately; the default is SIGKILL.
  • docker rm removes a stopped container's metadata and writable container state.

A restart policy can restart containers after certain exits, but it does not repair the underlying failure.

Debugging lab

docker run -d --name signal-lab alpine sleep 300
docker inspect signal-lab
docker stop -t 5 signal-lab
docker inspect signal-lab --format '{{.State.ExitCode}}'
docker rm signal-lab

Interview questions

  • Why does PID 1 matter?
  • Why might a process ignore SIGTERM?
  • Why can exit code 137 indicate SIGKILL without proving an OOM kill?
  • How do you design a containerized service for graceful shutdown?

Lesson 6 — Docker networking internals

6.1 The Linux networking model

On a typical Linux Docker host, bridge networking can involve:

  • A network namespace for the container.
  • A virtual Ethernet pair (veth) connecting the container namespace to the host.
  • A Linux bridge connecting container interfaces.
  • IP routing and firewall/NAT rules for external connectivity and published ports.
  • DNS configuration and service discovery.

This is a simplified bridge-network architecture. Docker can also use host networking, overlay networking, macvlan, and other drivers. Docker Desktop adds another layer because containers generally run inside a Linux VM.

6.2 Network modes

+---------+---------------------------------------------------------------------------------+
| Mode    | Behavior                                                                        |
+---------+---------------------------------------------------------------------------------+
| Bridge  | Container uses an isolated network connected through a Linux bridge             |
| Host    | Container shares the host's network namespace on supported Linux configurations |
| None    | No ordinary external container network is configured                            |
| Overlay | Connects workloads across hosts through an overlay network implementation       |
| Macvlan | Gives containers interfaces with distinct MAC addresses on a physical network   |
+---------+---------------------------------------------------------------------------------+

6.3 Hands-on lab

docker network ls
docker network inspect bridge

docker network create app-net

docker run -d --name web --network app-net nginx
docker run --rm --network app-net alpine \
  wget -qO- http://web

docker network inspect app-net
docker rm -f web
docker network rm app-net

The Alpine request should return the Nginx response if the containers can resolve one another and communicate normally.

Inspect Linux networking:

ip addr
ip route
ip link
ss -lntp

For packet-level debugging, learn tcpdump, ip netns, conntrack, and nft or iptables, as available on your host.

6.4 Production debugging method

If a service is unreachable, test each layer:

  1. Is the application listening on the expected address and port?
  2. Does the container have the expected IP and route?
  3. Can another container resolve the service name?
  4. Can the client reach the destination IP and port?
  5. Is the host port published?
  6. Are firewall rules, routing, MTU, or connection tracking causing the failure?

Common trap: an application listening only on 127.0.0.1 inside its container is not ordinarily reachable through the container's external interface. A service intended for container-to-container access typically needs to listen on the appropriate interface, often 0.0.0.0.

  • Why does localhost inside a container not mean the Docker host?
  • How would you diagnose intermittent DNS failures?
  • How does Docker Desktop networking differ from native Linux Docker?

Lesson 7 — Storage, OverlayFS, and persistence

7.1 Image layers versus writable layers

In a common Linux installation using OverlayFS, image layers are read-only lower layers, and a container's changes are recorded in an upper writable layer.

OverlayFS presents a merged filesystem view. When a file from a lower layer is modified, copy-up behavior can place a writable copy in the upper layer.

This can be convenient, but it has performance and storage implications.

A container's writable layer is not a substitute for a durable data-management strategy.

7.2 Storage types

+--------------------------+-------------------------------------------------------------+
| Type                     | Best suited for                                             |
+--------------------------+-------------------------------------------------------------+
| Writable container layer | Ephemeral application changes                               |
| Named volume             | Persistent container data managed by Docker                 |
| Bind mount               | Sharing an explicit host path                               |
| `tmpfs` mount            | Temporary in-memory files on supported Linux configurations |
+--------------------------+-------------------------------------------------------------+

Hands-on lab

docker volume create db-data

docker run -d --name db-lab \
  -e POSTGRES_PASSWORD=example \
  -v db-data:/var/lib/postgresql/data \
  postgres:17

docker inspect db-lab
docker volume inspect db-data
docker stop db-lab
docker rm db-lab

For a disposable learning environment, use a non-production password and do not expose the database port.

Recreate the container using the same volume:

docker run -d --name db-lab \
  -e POSTGRES_PASSWORD=example \
  -v db-data:/var/lib/postgresql/data \
  postgres:17

Data in the volume should survive removal of the original container. A volume alone, however, is not a backup.

Clean up the lab:

docker rm -f db-lab
docker volume rm db-data

7.3 Production failure scenarios

Scenario A: Disk fills up

Investigate:

docker system df -v
docker ps -a
docker inspect <container_name>
df -h
df -i

Check both byte capacity and inode exhaustion. Review logs, writable layers, volumes, and the container runtime's storage directory.

Scenario B: Database loses data after recreation

Check whether the database stored data in its writable container layer instead of a persistent volume. Verify the mount destination and actual database data directory.

Scenario C: Unexpectedly slow filesystem writes

Investigate underlying disk latency, write amplification, page cache behavior, OverlayFS copy-up, bind mounts, and volume storage characteristics.

Interview questions

  • What is the difference between a volume and a bind mount?
  • Explain OverlayFS lower, upper, and merged directories.
  • Why can large writes to a container's writable layer be problematic?
  • Why does removing a container not normally remove its named volumes?
  • What is the difference between persistence and backup?

References: Docker storage, Linux OverlayFS.

Lesson 8 — CPU, memory, and performance

8.1 CPU controls

On Linux, the cgroup CPU controller can restrict a workload's CPU bandwidth.

For cgroups v2, cpu.max commonly contains a quota and period:

50000 100000

This example represents 50,000 microseconds of CPU time per 100,000-microsecond period, equivalent to 0.5 CPU of sustained bandwidth.

That does not guarantee a dedicated half-core assignment. It is a bandwidth limit.

Create a test container:

docker run -d --name cpu-lab \
  --cpus=0.5 alpine sleep 600

docker stats cpu-lab
docker inspect cpu-lab

Clean up:

docker rm -f cpu-lab

8.2 Memory controls

Memory usage and memory limits are different quantities. A container can be under its memory limit while using substantial page cache, or it can encounter memory pressure before the host runs out of all available memory.

The cgroups v2 memory controller can expose files such as:

  • memory.current
  • memory.max
  • memory.events
  • memory.stat

Their exact location depends on the container's cgroup membership and the host's cgroup mount.

8.3 OOM debugging

docker inspect <container_name> \
  --format '{{.State.OOMKilled}} {{.State.ExitCode}}'

docker stats
journalctl -k

Kernel log access may require elevated permissions. On production systems, also check the container platform's events and monitoring.

An exit code of 137 alone does not establish that the kernel OOM killer was responsible.

8.4 Performance methodology

When a container becomes slow:

  1. Establish a baseline and reproduce the problem.
  2. Check CPU utilization and throttling.
  3. Check memory usage, reclaim, and OOM events.
  4. Check filesystem and network latency.
  5. Inspect application-level queueing and thread or connection pools.
  6. Change one variable at a time.
  7. Compare measurements after the change.

Interview questions

  • Why can CPU throttling increase tail latency?
  • How do you distinguish an application memory leak from a cgroup memory limit?
  • What evidence confirms an OOM kill?
  • What is the difference between a CPU limit and CPU weight?
  • How can page cache affect observed memory usage?

References: Cgroups v2, Docker resource constraints.

Lesson 9 — Docker security

Security should be treated as a set of independent controls, not as a property automatically provided by using containers.

9.1 The main attack surfaces

  • Container processes running with unnecessary privileges.
  • The Docker daemon and access to its control socket.
  • Dangerous bind mounts, especially sensitive host paths.
  • Exposed secrets and credentials in images.
  • Vulnerable base images and application dependencies.
  • Excessive Linux capabilities.
  • Kernel vulnerabilities affecting shared-kernel isolation.
  • Insecure image provenance and registry credentials.

Access to a rootful Docker daemon is particularly sensitive: a user who can control that daemon can often obtain root-level control over the host.

9.2 Hardening checklist

+--------------------------------------------+--------------------------------------------------------------------+
| Control                                    | Purpose                                                            |
+--------------------------------------------+--------------------------------------------------------------------+
| Non-root user                              | Reduce process privileges                                          |
| Drop capabilities                          | Remove unnecessary privileged operations                           |
| Seccomp                                    | Restrict system calls                                              |
| AppArmor or SELinux                        | Apply additional access-control policies                           |
| Read-only root filesystem                  | Prevent unintended filesystem writes                               |
| Resource limits                            | Reduce resource-exhaustion risk                                    |
| Secret mounts or external secret managers  | Avoid baking secrets into images                                   |
| Image scanning and patching                | Identify and remediate known vulnerabilities                       |
| Digest pinning and provenance verification | Improve artifact integrity and traceability                        |
| Rootless mode                              | Reduce daemon and container privileges in supported configurations |
+--------------------------------------------+--------------------------------------------------------------------+

9.3 Example of a hardened container

docker run --rm \
  --user 10001:10001 \
  --cap-drop=ALL \
  --security-opt=no-new-privileges:true \
  --read-only \
  --tmpfs /tmp:rw,noexec,nosuid,size=16m \
  --memory=256m \
  --cpus=1 \
  alpine id

This is a demonstration, not a universal production command. Some applications require specific capabilities, writable paths, or additional permissions. Validate compatibility before enforcing these controls.

9.4 Security interview questions

  • What risks arise from mounting /var/run/docker.sock inside a container?
  • What is the difference between root inside a user namespace and root on the host?
  • What are Linux capabilities?
  • What does no-new-privileges prevent?
  • What is the difference between vulnerability scanning and image-signature verification?
  • When would you choose a VM instead of a container for an untrusted workload?

Reference: Docker security.

Lesson 10 — Docker Compose and multi-service applications

10.1 Why Compose exists

A real application often consists of multiple services:

  • An API server.
  • A database.
  • A cache.
  • A worker.
  • A message broker.

Docker Compose lets you describe and operate this collection using a declarative YAML configuration.

Example: API, PostgreSQL, and Redis

services:
  api:
    build: .
    ports:
      - "8080:8080"
    environment:
      DATABASE_URL: postgres://app:devpassword@db:5432/app
      REDIS_HOST: redis
    depends_on:
      db:
        condition: service_healthy
      redis:
        condition: service_healthy

  db:
    image: postgres:17
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: devpassword
      POSTGRES_DB: app
    volumes:
      - postgres-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d app"]
      interval: 5s
      timeout: 3s
      retries: 10

  redis:
    image: redis:7
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 10

volumes:
  postgres-data:

This example uses development credentials. For production, do not hardcode credentials in a Compose file committed to source control.

The example assumes the application listens on port 8080 and understands the configured environment variables.

10.2 Commands

docker compose config
docker compose up -d --build
docker compose ps
docker compose logs -f api
docker compose exec api sh
docker compose down

docker compose down -v additionally removes the Compose-managed named volumes. Avoid it when the data needs to persist.

10.3 Dependency versus readiness

depends_on can express startup dependencies. With a health-check condition, Compose can wait for the dependency to become healthy before starting the dependent service.

However, this does not remove the need for application-level resilience. A database can become unavailable after startup. Applications should implement connection retries, bounded timeouts, reconnection behavior, and graceful failure handling.

Interview questions

  • Why should applications not use container IP addresses as permanent identities?
  • What is the difference between service startup and readiness?
  • How do you handle database failure after the API has started?
  • How would you prevent connection storms after a dependency recovers?
  • When would you use Compose instead of Kubernetes?

Reference: Docker Compose.

Lesson 11 — Production operations

This lesson focuses on what you would do when a containerized service fails in production.

11.1 Essential operational commands

+------------------------+----------------------------------------------------------+
| Command                | What to investigate                                      |
+------------------------+----------------------------------------------------------+
| `docker ps -a`         | Running and stopped containers                           |
| `docker inspect`       | State, configuration, mounts, network, resource settings |
| `docker logs`          | Application output                                       |
| `docker stats`         | Resource usage                                           |
| `docker events`        | Runtime lifecycle events                                 |
| `docker top`           | Processes visible in the container                       |
| `docker exec`          | Run a diagnostic process in a running container          |
| `docker system df -v`  | Docker-managed disk usage                                |
| `journalctl -u docker` | Docker daemon logs on applicable systemd installations   |
+------------------------+----------------------------------------------------------+

Do not assume docker exec is available when a container has already exited. In that case, inspect logs, metadata, exit status, and reproduce the issue with a diagnostic configuration.

11.2 Health checks

A container can be running while its application is unusable. Health checks help distinguish process existence from application health.

Example:

HEALTHCHECK --interval=30s --timeout=3s \
  --start-period=20s --retries=3 \
  CMD curl -fsS http://localhost:8080/health || exit 1

This example assumes curl exists in the image and the application exposes that endpoint.

Health status does not automatically mean Docker will restart an unhealthy container. Restart policies and orchestration behavior are separate concerns.

11.3 Graceful shutdown

A robust service should:

  1. Receive the configured termination signal.
  2. Stop accepting new work.
  3. Finish or cancel in-flight requests within a deadline.
  4. Close database and broker connections.
  5. Flush critical telemetry.
  6. Exit before the termination grace period expires.

Incident simulation

Incident: API latency spikes after a deployment, and some containers restart.

Investigate in this order:

docker ps -a
docker inspect <container>
docker logs --since 30m <container>
docker stats
docker events

Then correlate the deployment time with resource usage, application errors, dependency latency, health-check failures, and exit reasons.

Do not immediately increase memory limits or restart every container. First establish whether the failure is caused by a resource constraint, a regression, a dependency outage, or an incorrect health check.

Interview questions

  • How would you investigate a restart loop?
  • What should a health endpoint test?
  • How would you distinguish liveness from readiness?
  • How would you roll out a new image without causing an outage?
  • What metrics would you collect from a container platform?

Lesson 12 — Kubernetes and the container runtime ecosystem

You do not need to become a Kubernetes expert to master Docker, but an IC4 engineer should understand where Docker ends and orchestration begins.

12.1 The distinction

  • Docker Engine: builds images and manages containers on a host.
  • containerd: provides container lifecycle and execution functionality.
  • OCI runtime: creates and starts container processes.
  • Kubernetes: orchestrates workloads across a cluster, including scheduling, service discovery, rollout management, and recovery.

Modern Kubernetes deployments generally use a CRI-compatible runtime such as containerd. Docker Engine is not the default direct runtime interface in modern Kubernetes; the old built-in dockershim was removed in Kubernetes 1.24. Docker-built images can still be used by compatible OCI image runtimes.

Some commands require elevated privileges. perf, tcpdump, and namespace operations may also be restricted by kernel configuration or security policy.

13.2 Trace application system calls

Install strace using your distribution's package manager if necessary.

For a running process:

strace -f -p <host_pid>

To trace a new command:

strace -f -o trace.log sh -c 'cat /etc/hosts'

Look for failed system calls such as EACCES, ENOENT, and ECONNREFUSED. Interpret them in context: the same error can arise from different underlying causes.

13.3 Enter a container's namespaces

On a native Linux Docker host, you can inspect the host PID:

docker inspect \
  --format '{{.State.Pid}}' <container_name>

Then, with suitable permissions:

sudo nsenter -t <host_pid> -n ip addr
sudo nsenter -t <host_pid> -n ip route
sudo nsenter -t <host_pid> -m findmnt

These commands enter the target process's network or mount namespace for inspection. They do not necessarily reproduce every aspect of the container's original execution environment.

On Docker Desktop, the container's Linux host PID may belong to the Linux VM rather than your macOS or Windows host.

13.4 Debugging scenario

A container cannot read a configuration file.

A systematic investigation:

  1. Verify the file exists in the image or mounted path.
  2. Inspect docker inspect for bind mounts and mount destinations.
  3. Inspect file permissions and the effective container user.
  4. Check mount flags and read-only settings.
  5. Trace the failing operation with strace if necessary.
  6. Consider SELinux or AppArmor denials where applicable.

14.2 Core design decisions

Scheduling: Place workloads based on CPU, memory, affinity, capacity, and failure-domain requirements. Avoid packing every workload onto one node.

Isolation: Apply namespace, cgroup, capability, syscall, and filesystem restrictions. Use stronger isolation, potentially including VMs, for workloads with a higher trust boundary requirement.

Image delivery: Build once, test the artifact, scan it, and deploy an immutable digest. Use caching and prefetching where they improve rollout performance.

Health and recovery: Distinguish a failed process from a failed node. Restart a failed workload when appropriate, but avoid infinite restart loops and synchronized retry storms.

Networking: Separate workload identity from transient IP addresses. Provide service discovery and policy enforcement.

Observability: Collect resource usage, restarts, scheduling failures, image-pull errors, application logs, and deployment events.

Capacity: Reserve resources for system processes and leave headroom for bursts, recovery, and node maintenance.

14.3 Capacity calculation

Suppose a worker node has 16 CPU cores and 64 GiB RAM. You reserve 2 cores and 8 GiB for system overhead, leaving 14 cores and 56 GiB for workload allocation.

If every workload requests 0.5 CPU and 1 GiB RAM:

  • CPU capacity: 14/0.5=2814 / 0.5 = 2814/0.5=28 workloads.
  • Memory capacity: 56/1=5656 / 1 = 5656/1=56 workloads.

The CPU request is the limiting factor, so the theoretical maximum is 28 workloads per node before accounting for other constraints. Real capacity should be lower when you need operational headroom or have additional workload requirements.

This illustrates why resource allocation is not simply a count of how many containers can be started.

  5. How would you recover from a control-plane outage?
