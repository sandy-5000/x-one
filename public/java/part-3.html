You want to understand how Java concurrency works, why race conditions happen, how to make shared state safe, and how to design concurrent backend code without creating deadlocks or performance bottlenecks.

2. Process vs Thread

First establish the mental model.

Process

A process is an independently running program.

For example:

Java Application
     |
     +---- Process
             |
             +---- Heap
             +---- Code
             +---- Resources
             +---- Threads

Thread

A thread is an execution path inside a process.

One Java application can have:

Java Process
   |
   +-- Thread 1
   +-- Thread 2
   +-- Thread 3
   +-- Thread 4

Threads within the same process generally share:

  • heap
  • objects
  • static variables

But each thread has its own:

  • stack
  • program counter
  • execution state

This shared-memory model is what makes concurrency powerful and dangerous.

3. Creating a Thread

There are several approaches you'll encounter.

Extending Thread

class MyThread extends Thread {

    @Override
    public void run() {
        System.out.println("Running...");
    }
}

Then:

MyThread thread = new MyThread();
thread.start();

Important

This:

thread.start();

creates/schedules a new thread of execution.

This:

thread.run();

does not create a new thread.

It simply calls the method normally.

4. Runnable

More commonly:

Runnable task = () -> {
    System.out.println("Running task");
};

Thread thread = new Thread(task);
thread.start();

Why is Runnable generally preferable?

Because your task and your thread are separate concepts.

+-------------------+
|      Runnable     |
+-------------------+
          |
          v
          |
          |
          v
  | represents work
          |
          v
+-------------------+
|  Executor/Thread  |
+-------------------+
          |
          v
          |
          |
          v
   | executes work
          |
          v
+-------------------+
|        CPU        |
+-------------------+

This separation becomes extremely important when you learn thread pools.

6. start() vs run()

This is a classic interview question.

start()

thread.start();

Requests JVM to execute the thread concurrently.

run()

thread.run();

ordinary method invocation.

Example:

Thread t = new Thread(() -> {
    System.out.println(Thread.currentThread().getName());
});

t.start();

versus:

t.run();

The second one executes on the current thread.

7. sleep()

Thread.sleep(1000);

Pauses the currently executing thread for approximately one second.

Important:

sleep() does not release a monitor lock that the thread already owns.

This matters when you're dealing with synchronization.

8. join()

join() allows one thread to wait for another thread to finish.

Thread t = new Thread(() -> {
    System.out.println("Working...");
});

t.start();

t.join();

System.out.println("Finished");

Conceptually:

Main Thread
    |
    +---- start Worker
    |
    +---- wait at join()
    |
    |       Worker
    |          |
    |          +---- work
    |          +---- terminate
    |
    +---- continue

Know this well.

9. Interrupts

Learn:

thread.interrupt();

and:

Thread.currentThread().isInterrupted();

An interrupt is a request for a thread to stop/wake from interruptible operations; it isn't a forceful kill.

Example:

while (!Thread.currentThread().isInterrupted()) {
    // work
}

Also understand:

InterruptedException

and why you generally should not silently swallow it.

Typical pattern:

try {
    Thread.sleep(1000);
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
}

10. The Most Important Problem: Shared State

Consider:

class Counter {

    private int count = 0;

    void increment() {
        count++;
    }

    int getCount() {
        return count;
    }
}

Now:

Counter counter = new Counter();

Thread t1 = new Thread(() -> {
    for (int i = 0; i < 10000; i++) {
        counter.increment();
    }
});

Thread t2 = new Thread(() -> {
    for (int i = 0; i < 10000; i++) {
        counter.increment();
    }
});

You might expect:

20000

But you may get something lower.

Why?

Because:

count++;

isn't one indivisible operation.

Conceptually:

+-------------+
|  read count |
+-------------+
       |
       v
+-------------+
|    add 1    |
+-------------+
       |
       v
+-------------+
| write count |
+-------------+

Two threads can interleave these operations.

11. Race Condition

A race condition occurs when program behavior depends on the timing/interleaving of concurrent operations.

Example:

count = 10

Thread A: read 10
Thread B: read 10

Thread A: 10 + 1 = 11
Thread B: 10 + 1 = 11

Thread A: write 11
Thread B: write 11

Expected:

12

Actual:

11

This is one of the most important concepts in this week's lab.

12. Critical Section

A critical section is code that accesses shared state and must be protected from unsafe concurrent access.

Example:

void increment() {
    count++;
}

If multiple threads modify count, this becomes a critical section.

The goal is to ensure appropriate synchronization around it.

13. synchronized

The simplest Java synchronization mechanism.

public synchronized void increment() {
    count++;
}

Now only one thread at a time can execute that synchronized instance method for the same object.

14. Synchronized Block

Instead of synchronizing the entire method:

public void increment() {

    synchronized (this) {
        count++;
    }
}

This allows you to control exactly what is protected.

This is often preferable when only a small portion needs synchronization.

15. What Does synchronized Actually Do?

You should understand this beyond "it makes code thread-safe."

synchronized provides two important guarantees:

Mutual exclusion

Only one thread can hold the same monitor at a time.

Visibility

Changes made by one thread while holding/releasing the monitor become visible to another thread that subsequently acquires the same monitor.

Think:

+----------------------------------+
|             Thread A             |
+----------------------------------+
                  |
                  v
                 |
                  |
                  v
           | synchronized
                  |
                  v
+----------------------------------+
|               LOCK               |
+----------------------------------+
                  |
                  v
                 |
                  |
                  v
+----------------------------------+
|       modify shared state        |
+----------------------------------+
                  |
                  v
                 |
                  |
                  v
+----------------------------------+
|              UNLOCK              |
+----------------------------------+
                  |
                  v
                 |
                  |
                  v
+----------------------------------+
|             Thread B             |
+----------------------------------+
                  |
                  v
                 |
                  |
                  v
           | synchronized
                  |
                  v
+----------------------------------+
| sees appropriate published state |
+----------------------------------+

16. Intrinsic Locks / Monitors

Every Java object can be associated with an intrinsic monitor lock.

For:

synchronized (obj) {
    // critical section
}

the thread attempts to acquire obj's monitor.

Only one thread can hold that monitor at a time.

17. Instance Method Synchronization

class Counter {

    private int count;

    public synchronized void increment() {
        count++;
    }
}

This is effectively associated with:

synchronized (this)

So the lock is the particular Counter object.

18. Static Synchronized Method

Consider:

public static synchronized void foo() {
}

This synchronizes on the Class object.

Conceptually:

synchronized (Counter.class) {
    // ...
}

This distinction is important.

Instance synchronized

lock = this

Static synchronized

lock = Counter.class

19. Different Locks

Suppose:

Counter c1 = new Counter();
Counter c2 = new Counter();

If:

c1.increment();
c2.increment();

and increment() is an instance synchronized method, the threads can potentially execute concurrently because:

+----+--------+
| c1 | lock A |
+----+--------+
+----+--------+
| c2 | lock B |
+----+--------+

They aren't fighting over the same monitor.

20. volatile

Another very important keyword:

private volatile boolean running = true;

volatile primarily addresses visibility and ordering guarantees for a variable.

Example:

class Worker implements Runnable {

    private volatile boolean running = true;

    public void stop() {
        running = false;
    }

    public void run() {
        while (running) {
            // work
        }
    }
}

Without appropriate visibility guarantees, another thread's update may not be observed as expected.

21. volatile Does NOT Make Everything Atomic

This is extremely important.

volatile int count;

count++;

is still unsafe as a compound operation.

Why?

read
+
write

can still interleave.

So:

volatile

is not equivalent to:

synchronized

22. Atomic Classes

Java provides:

AtomicInteger
AtomicLong
AtomicBoolean
AtomicReference

Example:

AtomicInteger counter = new AtomicInteger();

counter.incrementAndGet();

Instead of:

counter++;

You can use atomic operations.

Useful methods include:

incrementAndGet()
getAndIncrement()
decrementAndGet()
getAndDecrement()
compareAndSet()
get()
set()

23. Compare-and-Set / CAS

You should understand the idea behind CAS.

Conceptually:

current value = 10

"Change 10 → 11 only if it is still 10"

If another thread changed it:

CAS fails

The operation can then retry.

This is a fundamental concept behind many lock-free/concurrent algorithms.

24. synchronized vs Atomic Classes

synchronized

Useful when you have:

multiple operations
+
multiple shared variables
+
invariants

Example:

synchronized void transfer(Account from, Account to, int amount) {
    ...
}

AtomicInteger

Excellent for simple atomic state transitions:

counter.incrementAndGet();

Don't blindly replace every synchronization block with atomics.

25. Lock

Java also provides explicit locking:

Lock lock = new ReentrantLock();

Example:

lock.lock();

try {
    // critical section
} finally {
    lock.unlock();
}

The finally is critical.

You don't want:

lock.lock();

// exception

lock.unlock();

because the lock may remain held.

26. ReentrantLock

Know these methods:

lock()
unlock()
tryLock()
lockInterruptibly()

tryLock() can be especially useful:

if (lock.tryLock()) {
    try {
        // work
    } finally {
        lock.unlock();
    }
}

Unlike blindly waiting forever, you can decide what to do if the lock isn't available.

27. Reentrant

"Reentrant" means the same thread can acquire the same lock multiple times.

Conceptually:

Thread A
   |
   acquire lock
   |
   acquire same lock again
   |
   release
   |
   release

The lock maintains ownership/reentrancy information.

28. ReadWriteLock

Useful when you have:

many readers
few writers

Example:

ReadWriteLock lock = new ReentrantReadWriteLock();

You get:

lock.readLock()
lock.writeLock()

Multiple readers can potentially read concurrently.

Writers require exclusive access.

29. StampedLock

Know that it exists, but don't spend too much Week 3 time on it.

It supports:

  • read locks
  • write locks
  • optimistic reads

It is more advanced and has important caveats.

For your current preparation:

Understand the concept; don't prioritize mastering it yet.

30. Thread Coordination

Concurrency isn't only about locking.

Threads often need to communicate.

Learn:

wait()
notify()
notifyAll()

Example:

synchronized (queue) {

    while (queue.isEmpty()) {
        queue.wait();
    }

    // consume
}

Producer:

synchronized (queue) {

    queue.add(item);

    queue.notifyAll();
}

31. Why while, Not if?

This is important:

while (queue.isEmpty()) {
    queue.wait();
}

rather than:

if (queue.isEmpty()) {
    queue.wait();
}

After waking up, the condition must be checked again.

This is a classic concurrency concept.

32. wait() vs sleep()

Know this table:

+---------------------------------------+-----------------------------------+
| `wait()`                              | `sleep()`                         |
+---------------------------------------+-----------------------------------+
| Used for coordination                 | Used for timing                   |
| Must be called with monitor ownership | Doesn't require monitor ownership |
| Releases the monitor while waiting    | Does not release monitor          |
| Usually used with `notify/notifyAll`  | No notification mechanism         |
| Defined on `Object`                   | Defined on `Thread`               |
+---------------------------------------+-----------------------------------+

This is a common interview question.

33. Why Modern Code Usually Avoids Manual wait/notify

Although you should understand them, modern Java code often uses higher-level concurrency utilities:

BlockingQueue
ExecutorService
CompletableFuture
CountDownLatch
Semaphore
CyclicBarrier
Phaser

These reduce the amount of error-prone coordination code.

34. ExecutorService

This is one of the highest-priority topics for your Week 3 lab.

Instead of:

new Thread(...).start();
new Thread(...).start();
new Thread(...).start();

use a thread pool.

ExecutorService executor =
        Executors.newFixedThreadPool(4);

Then:

executor.submit(() -> {
    System.out.println("Task");
});

And eventually:

executor.shutdown();

35. Why Thread Pools?

Creating a thread has overhead.

Suppose you receive:

100,000 requests

You don't want:

100,000 threads

Instead:

+---------------------------+
|          Requests         |
+---------------------------+
              |
              v
+---------------------------+
|         Task queue        |
+---------------------------+
              |
              v
+---------------------------+
|        Thread pool        |
+---------------------------+
              |
              v
+---------------------------+
| 4 / 8 / 16 worker threads |
+---------------------------+

Threads are reused.

36. Executor Architecture

Understand:

                +----------------+
Tasks --------> |   Work Queue   |
                +-------+--------+
                        |
          +-------------+-------------+
          |             |             |
       Worker 1      Worker 2      Worker 3
          |             |             |
        Task          Task          Task

This is fundamental backend concurrency architecture.

37. Executor Types

Know:

Executors.newFixedThreadPool(n)
Executors.newSingleThreadExecutor()
Executors.newCachedThreadPool()

Also understand why blindly using Executors factory methods can be problematic in production systems due to their queue/thread behavior.

At IC4 level, you should be able to reason about:

  • number of workers
  • queue size
  • task duration
  • CPU vs I/O workload
  • rejection behavior
  • shutdown

38. Runnable vs Callable

Runnable

Doesn't return a result.

Runnable task = () -> {
    System.out.println("Hello");
};

Callable

Returns a value and can throw checked exceptions.

Callable<Integer> task = () -> {
    return 42;
};

39. Future

Submit a Callable:

Future<Integer> future =
        executor.submit(() -> 42);

Then:

Integer result = future.get();

But:

future.get();

can block.

This is important.

40. Future Cancellation

Know:

future.cancel(true);
future.isDone();
future.isCancelled();

But cancellation is cooperative in important practical respects; interrupting a task doesn't magically terminate arbitrary code.

41. CompletableFuture

This is extremely useful for backend development.

Example:

CompletableFuture
    .supplyAsync(() -> getUser())
    .thenApply(user -> user.getName())
    .thenAccept(System.out::println);

You can compose asynchronous operations.

future.thenCompose(

           v

Future<Future<List<Order>>>

45. Concurrent Collections

Learn these thoroughly:

ConcurrentHashMap
CopyOnWriteArrayList
BlockingQueue
ConcurrentLinkedQueue

46. ConcurrentHashMap

Don't do this blindly:

Map<String, Integer> map =
        new HashMap<>();

and access it concurrently.

Instead:

ConcurrentHashMap<String, Integer> map =
        new ConcurrentHashMap<>();

It provides thread-safe concurrent access with much better concurrency characteristics than synchronizing an entire HashMap for every operation.

47. Atomic Map Operations

This is especially useful:

map.computeIfAbsent(key, k -> createValue());

Also:

map.compute()
map.merge()
map.putIfAbsent()

These operations help avoid unsafe check-then-act sequences.

Bad:

if (!map.containsKey(key)) {
    map.put(key, value);
}

Prefer an atomic map operation where appropriate.

48. BlockingQueue

Extremely important for producer-consumer architecture.

Example:

BlockingQueue<Task> queue =
        new LinkedBlockingQueue<>();

Producer:

queue.put(task);

Consumer:

Task task = queue.take();

take() waits if the queue is empty.

49. Producer-Consumer Pattern

Understand this deeply.

  Producer 1 ----\
+------------------+     +-------+     +------+
| Producer 2 ----- | --> | Queue | --> | Cons |
+------------------+     +-------+     +------+
  Producer 3 ----/           Con

This pattern appears everywhere in backend systems.

It provides:

  • decoupling
  • buffering
  • controlled concurrency
  • backpressure opportunities

50. CountDownLatch

Useful when one or more threads must wait until several operations complete.

Example:

CountDownLatch latch =
        new CountDownLatch(3);

Workers:

latch.countDown();

Waiting thread:

latch.await();

Concept:

  Worker A ──┐
+----------------+---------------+
| Worker B ──┼── | latch reaches |
+----------------+---------------+
  Worker C ──┘

51. Semaphore

Controls the number of concurrent permits.

Semaphore semaphore =
        new Semaphore(5);

Concept:

Only 5 threads can enter
the protected resource simultaneously.

Useful for limiting:

  • database connections
  • external API calls
  • expensive resources

52. CyclicBarrier

Allows several threads to wait until all reach a barrier.

Concept:

Thread A ----\
Thread B -----+---- barrier ---- continue
Thread C ----/

Unlike CountDownLatch, a barrier can be reused.

53. Deadlock

One of the most important concurrency bugs.

Imagine:

Thread A:
  lock A
  wait for lock B

Thread B:
  lock B
  wait for lock A

Neither can continue.

+---+     +--------------+     +-------------+
| A | --> | holds Lock 1 | --> | waits for L |
+---+     +--------------+     +-------------+
+---+     +--------------+     +-------------+
| B | --> | holds Lock 2 | --> | waits for L |
+---+     +--------------+     +-------------+

Deadlock.

54. Four Conditions for Deadlock

Know these:

  1. Mutual exclusion
  2. Hold and wait
  3. No preemption
  4. Circular wait

If all four exist, deadlock can occur.

55. Preventing Deadlock

One powerful strategy:

Consistent lock ordering

Always acquire:

Lock A
then
Lock B

Never:

  Thread 1:
+---+---+
| A | B |
+---+---+
  Thread 2:
+---+---+
| B | A |
+---+---+

Instead:

  Thread 1:
+---+---+
| A | B |
+---+---+
  Thread 2:
+---+---+
| A | B |
+---+---+

This breaks circular waiting.

56. Starvation

A thread may continually fail to obtain the resources/CPU time it needs.

Example:

+-----------------------------------+
|              Thread A             |
+-----------------------------------+
                  |
                  v
+-----------------------------------+
|              Thread B             |
+-----------------------------------+
                  |
                  v
+-----------------------------------+
|              Thread C             |
+-----------------------------------+
                  |
                  v
+-----------------------------------+
| Thread A repeatedly gets the lock |
+-----------------------------------+
                  |
                  v
+-----------------------------------+
|        B/C rarely progress        |
+-----------------------------------+

That's starvation.

57. Livelock

Threads aren't blocked, but they keep responding to each other without making meaningful progress.

Think:

Thread A: "I'll step aside."
Thread B: "I'll step aside."
Thread A: "I'll step aside."
Thread B: "I'll step aside."

Everyone is active.

Nothing gets done.

58. Thread Safety

A class is thread-safe when it behaves correctly when accessed concurrently according to its contract.

This is more useful than saying:

"It uses synchronized."

Thread safety can be achieved through:

  • synchronization
  • locks
  • atomic variables
  • immutability
  • confinement
  • concurrent collections
  • message passing

59. Immutability

One of the best concurrency strategies is:

Don't share mutable state.

Instead of:

class User {
    private String name;

    void setName(String name) {
        this.name = name;
    }
}

prefer immutable designs when appropriate:

final class User {

    private final String name;

    User(String name) {
        this.name = name;
    }

    public String getName() {
        return name;
    }
}

If state cannot change, synchronization becomes much simpler.

60. Thread Confinement

Another useful strategy:

+----------+---------------+
| Thread A | owns object A |
+----------+---------------+
+----------+---------------+
| Thread B | owns object B |
+----------+---------------+

Rather than:

Thread A \
Thread B  → shared mutable object
Thread C /

Avoid sharing when possible.

61. Java Memory Model — Important IC4 Topic

Don't skip this.

You need a conceptual understanding of:

  • visibility
  • atomicity
  • ordering
  • happens-before

Think about three separate questions:

Atomicity

Can the operation be observed halfway through?

Visibility

Will another thread see my update?

Ordering

Can operations appear reordered across threads?

These are different problems.

62. Happens-Before

You don't need to memorize every rule immediately.

Understand the concept:

If A happens-before B, the effects of A are guaranteed to be visible to B according to Java's memory model.

Important happens-before relationships include those established by:

  • unlocking a monitor → subsequent locking of same monitor
  • writing a volatile variable → subsequent reading of that variable
  • Thread.start() → actions in started thread
  • actions in a thread → successful join() return
  • appropriate completion/coordination mechanisms

This is a major conceptual foundation.

77. Concurrency vs Parallelism

Know the distinction.

Concurrency

Multiple tasks are in progress during overlapping periods.

Parallelism

Multiple tasks are literally executing simultaneously, typically on different CPU cores.

Conceptually:

+----------------+
|  Concurrency:  |
+----------------+
         |
         v
+----------------+
|     Task A     |
+----------------+
         |
         v
+----------------+
|     Task B     |
+----------------+
         |
         v
+----------------+
|  Parallelism:  |
+----------------+
         |
         v
+----------------+
| Core 1: Task A |
+----------------+
         |
         v
+----------------+
| Core 2: Task B |
+----------------+

Concurrency doesn't necessarily require multiple cores.

78. CPU-Bound vs I/O-Bound

This becomes important when deciding thread-pool sizes.

CPU-bound

Examples:

  • calculations
  • compression
  • image processing

Too many threads can cause excessive context switching.

I/O-bound

Examples:

  • database calls
  • HTTP calls
  • filesystem operations

Threads may spend significant time waiting.

Therefore, thread-pool sizing depends on workload.

Don't memorize:

"CPU cores × 2"

as a universal rule.

Learn to reason from:

CPU
+
I/O wait
+
latency
+
throughput
+
queueing
+
resource limits

79. Concurrency Design Principles

These are more valuable than memorizing APIs.

Principle 1

Minimize shared mutable state.

Principle 2

Prefer immutability.

Principle 3

Keep critical sections small.

Principle 4

Avoid holding locks during slow operations.

Principle 5

Use higher-level concurrency utilities.

Principle 6

Define ownership of mutable state.

Principle 7

Use consistent lock ordering.

Principle 8

Bound concurrency where external resources are limited.

Principle 9

Understand cancellation and shutdown.

Principle 10

Measure before optimizing concurrency.
