Week 2 — Java Collections + “Unknown Classes” + Collection Lab

For Week 2, the goal should be much deeper than memorizing ArrayList, HashMap, etc. For an IC4-level Java/Spring/backend role, you should understand how the collections work internally, their complexity, contracts, trade-offs, concurrency behavior, and how to choose the right collection in production code.

I’d structure the week like this:

Week 2 learning objectives

By the end of the week, you should be able to:

  1. Choose the right Java collection for a given problem.
  2. Explain the internal implementation of ArrayList, LinkedList, HashMap, HashSet, TreeMap, and TreeSet.
  3. Explain equals() / hashCode() and why they are critical for hash-based collections.
  4. Understand Comparable vs Comparator.
  5. Understand generics, wildcards, PECS, and type erasure.
  6. Understand Iterator, ListIterator, and fail-fast behavior.
  7. Understand immutable/unmodifiable collections.
  8. Understand Java's modern collection APIs (List.of, Set.of, Map.of, copyOf, Collectors.toList, etc.).
  9. Understand ConcurrentHashMap, concurrent collections, and when ordinary collections are unsafe.
  10. Solve collection-heavy coding problems without accidentally creating O(n²) solutions.
  11. Read an unfamiliar/“unknown” Java class and determine what it does from its API, inheritance, interfaces, and usage.

Part 2 — Iterable and Iterator

Understand:

Iterable<T>

and:

Iterator<T>

For example:

List<String> names = List.of("A", "B", "C");

for (String name : names) {
    System.out.println(name);
}

The enhanced for loop works because the object is Iterable.

Conceptually:

Iterator<String> iterator = names.iterator();

while (iterator.hasNext()) {
    String name = iterator.next();
}

Know:

hasNext()
next()
remove()
forEachRemaining()

Why Iterator exists

It separates:

"How do I traverse this collection?"

from:

"How is this collection internally implemented?"

You shouldn't need to know whether you're traversing an array, linked structure, tree, etc.

Part 6 — LinkedList

Conceptually:

10 <-> 20 <-> 30 <-> 40

Each node contains references to neighboring nodes.

Something like:

+--------+
|  Node  |
+--------+
     |
     v
+--------+
| ├ item |
+--------+
     |
     v
+--------+
| ├ next |
+--------+
     |
     v
+--------+
|  prev  |
+--------+

Advantages:

  • efficient insertion/removal when you already have the appropriate node/iterator position

Disadvantages:

  • poor random access
  • additional memory overhead
  • worse cache locality
  • often slower in real applications than people expect

Example:

list.get(50000);

This is not:

O(1)

Part 7 — ArrayList vs LinkedList

You should know this comparison extremely well.

+---------------------+----------------+------------+
| Operation           | ArrayList      | LinkedList |
+---------------------+----------------+------------+
| `get(index)`        | O(1)           | O(n)       |
| append              | O(1) amortized | O(1)       |
| insert at beginning | O(n)           | O(1)*      |
| remove beginning    | O(n)           | O(1)*      |
| memory locality     | good           | poor       |
| memory overhead     | lower          | higher     |
+---------------------+----------------+------------+

* assumes the appropriate node/position is already available; finding a position by index can itself cost O(n).

Interview question

Why wouldn't you automatically use LinkedList when you need lots of insertions?

Because "insertion is O(1)" is incomplete.

If you have:

list.add(50000, value);

finding that position is still O(n).

And in practice, ArrayList often performs better because arrays have excellent cache locality.

Part 8 — Set

A Set represents a collection of unique elements.

Set<String> names = new HashSet<>();

names.add("Alice");
names.add("Alice");
names.add("Bob");

Result:

Alice
Bob

Core question:

How does Java know that two objects are duplicates?

This leads directly to:

equals() + hashCode()

Part 9 — equals() and hashCode()

This is critical.

Suppose:

class Employee {
    int id;
    String name;
}

You create:

Employee e1 = new Employee(1, "John");
Employee e2 = new Employee(1, "John");

Without overriding equals():

e1.equals(e2)

is normally:

false

because they are different objects.

equals() contract

Know the major properties:

Reflexive

x.equals(x) == true

Symmetric

x.equals(y) == y.equals(x)

Transitive

If:

x == y
y == z

then:

x == z

Consistent

Repeated calls should produce the same result unless relevant state changes.

Null

x.equals(null)

should be:

false

Part 10 — hashCode()

If:

a.equals(b)

is true, then:

a.hashCode() == b.hashCode()

must also be true.

But the reverse isn't required.

Two objects can have:

same hash code

while:

equals() == false

That's a collision.

Part 14 — Hash Collisions

Two keys can produce the same bucket.

Example:

+------------+
|   key A    |
+------------+
       |
       v
+------------+
| ├ bucket 5 |
+------------+
       |
       v
+------------+
|   key B    |
+------------+

This is called a collision.

Java handles collisions using internal structures rather than assuming every hash is unique.

Understand:

A hash code is not an identity.

Part 15 — HashMap Mutable Key Trap

Extremely important interview topic.

Bad:

Map<Employee, String> map = new HashMap<>();

Employee employee = new Employee(1);

map.put(employee, "Developer");

employee.setId(2);

map.get(employee);

If id participates in:

equals()
hashCode()

changing it after insertion can make the key effectively unreachable.

Rule:

Don't mutate fields that participate in equality/hash identity while an object is being used as a hash-based collection key.

Part 19 — Comparable

A class can define its natural ordering using:

Comparable<T>

Example:

class Employee implements Comparable<Employee> {

    int salary;

    @Override
    public int compareTo(Employee other) {
        return Integer.compare(this.salary, other.salary);
    }
}

Then:

Collections.sort(employees);

can use the natural ordering.

Part 20 — Comparator

A Comparator allows external/custom ordering.

employees.sort(
    Comparator.comparing(Employee::getSalary)
);

Or:

employees.sort(
    Comparator.comparing(Employee::getName)
);

You can define multiple orderings without changing the class itself.

Part 21 — Comparable vs Comparator

Know this cold.

+--------------------------+----------------------------------+
| Comparable               | Comparator                       |
+--------------------------+----------------------------------+
| defines natural ordering | defines external/custom ordering |
| `compareTo()`            | `compare()`                      |
| class implements it      | separate object/lambda           |
| one primary ordering     | multiple possible orderings      |
+--------------------------+----------------------------------+

Example:

employees.sort(
    Comparator.comparing(Employee::getSalary)
             .thenComparing(Employee::getName)
);

Know:

thenComparing()
reversed()
nullsFirst()
nullsLast()

Part 32 — Type Erasure

Understand why:

and:

  • Java uses type erasure
  • you cannot generally do:

Part 33 — Immutable vs Unmodifiable Collections

Unmodifiable view

This creates a read-only view over another collection.

If the underlying collection changes, the view can reflect those changes.

This distinction is important.

Part 41 — ConcurrentHashMap

Know that it is designed for concurrent access.

Example:

    new ConcurrentHashMap<>();

Useful methods include:

putIfAbsent()

computeIfAbsent()

Understand the distinction between:

and:

thread-safe compound operation

For example, making individual map operations safe doesn't automatically make every multi-step business operation atomic.

Part 42 — CopyOnWriteArrayList

Understand its trade-off.

Excellent when:

many reads
few writes

Writes involve copying the underlying array.

Typical use cases include:

subscriber lists

Don't use it blindly for write-heavy workloads.

Part 43 — Collection Synchronization

Know:

Collections.synchronizedList(...)
Collections.synchronizedMap(...)
Collections.synchronizedSet(...)

and understand that synchronization wrappers don't magically make every sequence of operations atomic.

For example:

if (!map.containsKey(key)) {
    map.put(key, value);
}

is still a compound operation that requires appropriate synchronization/atomic APIs.

Part 44 — Fail-Fast Iterators

Understand:

ConcurrentModificationException

Example:

for (String name : names) {
    if (name.equals("Bob")) {
        names.remove(name);
    }
}

This can cause:

ConcurrentModificationException

Use an iterator correctly:

Iterator<String> iterator = names.iterator();

while (iterator.hasNext()) {
    if (...) {
        iterator.remove();
    }
}

Or use appropriate collection APIs.

Important:

Fail-fast behavior is a bug-detection mechanism, not a thread-safety guarantee.

Part 45 — Collection Complexity

| HashSet       | —         | O(1)*    | O(1)*    | O(1)*         | none        |
| LinkedHashSet | —         | O(1)*    | O(1)*    | O(1)*         | insertion   |

| LinkedHashMap | O(1)*     | O(1)*    | O(1)*    | O(1)*         | predictable |
