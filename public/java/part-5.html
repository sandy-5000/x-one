For an IC4-level Java/backend interview, you should be able to go beyond:

The JVM loads the binary representation of a class.

For example:

UserService

8. Parent Delegation Model

This is a very important interview topic.

Suppose your application asks to load:

java.lang.String

The application class loader doesn't simply load it itself.

It delegates upward.

Conceptually:

Application ClassLoader
        |
        v
Platform ClassLoader
        |
        v
Bootstrap ClassLoader

The parent gets the opportunity to load the class first.

Why?

Security

You shouldn't be able to replace:

with your own malicious version.

Consistency

Core classes should have a common definition.

11. Heap

The heap stores objects.

Example:

User user = new User();

The object generally lives on the heap:

Heap
+----------------+
| User object    |
| name reference |
| age            |
+----------------+

The variable:

user

is a reference held somewhere associated with the executing thread/frame, while the actual object is allocated in JVM-managed memory.

Don't oversimplify this as:

"All references are always on stack."

That isn't universally correct.

12. Heap is Shared

The heap is shared among JVM threads.

+-----------------+
|     Thread 1    |
+-----------------+
         |
         v
+-----------------+
| Thread 2 > Heap |
+-----------------+
         |
         v
+-----------------+
|     Thread 3    |
+-----------------+

Therefore:

new User()

creates an object in memory potentially accessible by multiple threads if references are shared.

This connects directly with your Week 3 concurrency material.

13. Stack

Every Java thread has its own JVM stack.

Example:

void calculate() {
    int x = 10;
    int y = 20;
}

Conceptually:

Thread
 |
 +-- Stack
      |
      +-- calculate() frame
             |
             +-- x
             +-- y

Each method invocation creates a stack frame.

14. Stack Frame

A JVM stack frame contains information associated with a method invocation.

Conceptually:

+-----------------------+
| Local variables       |
+-----------------------+
| Operand stack         |
+-----------------------+
| Frame data            |
+-----------------------+

For example:

int add(int a, int b) {
    return a + b;
}

The JVM uses local variables and the operand stack to execute bytecode.

16. Heap vs Stack

You should be able to explain this table:

+-----------------------+---------------------------+
| Stack                 | Heap                      |
+-----------------------+---------------------------+
| Per-thread            | Shared                    |
| Method frames         | Objects                   |
| Local execution state | Object memory             |
| Short-lived frames    | Objects may live long     |
| StackOverflowError    | OutOfMemoryError possible |
| Automatically popped  | Managed by GC             |
+-----------------------+---------------------------+

But avoid the simplistic statement:

"Primitive variables are always on the stack."

The JVM specification doesn't require that implementation strategy. JIT optimizations can eliminate allocations or move values around.

17. Metaspace

Metaspace stores JVM class metadata.

It replaced the old permanent generation approach in Java 8.

Conceptually:

+----------------+
|      Heap      |
+----------------+
         |
         v
+----------------+
|    Objects     |
+----------------+
         |
         v
+----------------+
|   Metaspace    |
+----------------+
         |
         v
+----------------+
| Class metadata |
+----------------+

For example:

class User {}

The runtime needs metadata describing:

  • class structure
  • methods
  • fields
  • runtime information

That information is associated with the class and managed outside the Java heap in modern HotSpot implementations.

In many HotSpot configurations, new objects are initially allocated in the young generation, often in a thread-local allocation buffer (TLAB).

22. TLAB

Thread Local Allocation Buffer

Instead of having every thread compete for a global allocation area:

+-------------------+
| Thread 1 > TLAB 1 |
+-------------------+
          |
          v
+-------------------+

Each thread gets a region from which it can rapidly allocate objects.

This makes allocation extremely cheap in the common case.

This is an important realization:

Java object allocation isn't inherently slow just because it uses a GC-managed heap.

Most objects die young.

28. Garbage Collection — The Core Idea

GC determines:

Which objects are no longer reachable?

Consider:

User user = new User();

user = null;

If there are no other references:

User object
    ↑
    |

It becomes eligible for collection.

Important:

Eligible for GC ≠ immediately collected.

29. Reachability

GC is fundamentally about reachability, not simply whether a variable is null.

Imagine:

GC Root
  |
  v
Object A
  |
  v
Object B

Both are reachable.

If:

GC Root
  |
  v
Object A

Object B

and B has no path from any GC root, B can be collected.

30. GC Roots

Important GC roots include things such as:

  • active thread references
  • local variables/references in active stack frames
  • static references
  • JNI references
  • certain JVM-internal references

Conceptually:

GC Roots
   |
   +----> Object A
   |        |
   |        +----> Object B
   |
   +----> Object C

Anything unreachable from roots can potentially be reclaimed.

31. Mark and Sweep

Basic GC algorithm:

Mark

Find reachable objects.

A ✓
B ✓
C ✗
D ✗

Sweep

Reclaim unreachable objects.

A
B
free
free

Problem:

Fragmentation

You can end up with:

Object | free | Object | free | Object

Large contiguous allocations may become difficult.

32. Mark + Compact

Another approach:

Before:

A | free | B | free | C | free

After compacting:

A | B | C | free | free | free

Benefits:

  • reduces fragmentation

Cost:

  • objects may need to be moved
  • references must be updated

33. Copying Collection

Another approach:

From Space
     |
     v
To Space

Live objects are copied.

This works especially well for young generations where most objects are dead.

34. Stop-the-World

A Stop-The-World (STW) pause means application threads are stopped for part of GC processing.

Application
██████████████

GC
              █████

Application
                    ███████████

During the pause:

+--------------------------+
| Java application threads |
+--------------------------+
              |
              v
+--------------------------+
|           STOP           |
+--------------------------+

This matters enormously for latency-sensitive applications.

35. Important Distinction

Don't say:

"GC always stops the world."

Modern collectors perform substantial work concurrently with application threads.

Instead:

Modern collectors can perform much of their work concurrently, but they still have some stop-the-world phases.

This distinction is frequently tested.

36. Safepoints

A safepoint is a state where JVM can safely perform certain runtime operations, including operations that require threads to reach a globally consistent state.

Examples can include:

  • some GC operations
  • deoptimization
  • certain JVM maintenance operations

A production pause isn't necessarily:

"GC is slow."

You should distinguish:

GC pause
vs
safepoint coordination delay
vs
application pause

37. Major GC vs Full GC

Be careful here.

Terminology such as:

minor GC
major GC
full GC

is not universally consistent across all collectors/JVM versions.

For interviews, say:

The exact meaning of "major GC" and "full GC" is collector-dependent. Full GC generally refers to a more comprehensive collection involving a larger portion of the heap and often more expensive work.

This is much safer than memorizing simplistic definitions.

38. GC Algorithms

You should know these concepts:

Serial
Parallel
G1
ZGC
Shenandoah

39. Serial GC

Single-threaded collector.

Good for:

  • small heaps
  • simple workloads
  • low overhead environments

Not generally chosen for large, latency-sensitive server workloads.

40. Parallel GC

Optimized primarily for throughput.

Conceptually:

Application
     |
     v
Parallel GC workers

Multiple GC threads perform collection work.

Goal:

maximize application throughput.

41. G1 GC

G1 = Garbage-First Garbage Collector

Instead of thinking primarily in contiguous generations, G1 divides the heap into regions.

Conceptually:

+----+----+----+----+----+
| R1 | R2 | R3 | R4 | R5 |
+----+----+----+----+----+
| R6 | R7 | R8 | R9 | R10|
+----+----+----+----+----+

Regions can play different roles.

G1 tracks region liveness and tries to collect regions that provide good reclamation value.

Hence:

Garbage First.

42. G1 Goal

G1 aims to balance:

throughput
+
predictable latency
+
large heaps

It allows you to specify a pause-time goal such as:

-XX:MaxGCPauseMillis=200

Important:

This is a goal, not a guarantee.

43. G1 Concurrent Marking

G1 can perform marking concurrently with application execution.

High-level:

Application
████████████████████████

Concurrent GC
    ███████████████

This reduces the amount of work requiring long global pauses.

44. ZGC

ZGC is designed for very low pause times, including large heaps.

Key idea:

Keep pauses extremely short while doing much of the GC work concurrently.

Conceptually:

Application
██████████████████████████

GC
  █████████████████████
  mostly concurrent

Useful for:

  • large heaps
  • latency-sensitive services
  • workloads where long GC pauses are unacceptable

But there are trade-offs involving CPU overhead and workload characteristics.

45. Shenandoah

Shenandoah is another low-pause collector.

Its major goal:

Perform most object relocation concurrently with application execution.

Both ZGC and Shenandoah are important to know conceptually for modern Java.

46. GC Comparison

A useful interview-level model:

+------------+------------------------------+
| Collector  | Main focus                   |
+------------+------------------------------+
| Serial     | Simplicity / small workloads |
| Parallel   | Throughput                   |
| G1         | Balanced server workloads    |
| ZGC        | Very low latency             |
| Shenandoah | Very low pause times         |
+------------+------------------------------+

Don't memorize this as an absolute rule.

Actual collector choice depends on:

  • Java version
  • heap size
  • workload
  • allocation rate
  • latency requirements
  • CPU budget
  • pause requirements

47. JIT Compilation

Now we move to one of the most important JVM concepts.

Initially, the JVM can interpret bytecode.

But interpreting every instruction forever would leave performance on the table.

So the JVM identifies frequently executed code and compiles it into native machine code.

That's:

Just-In-Time compilation.

48. Interpreter

Conceptually:

Bytecode
   |
   v
Interpreter
   |
   v
CPU execution

Simple and flexible.

But repeated interpretation has overhead.

49. JIT

Instead:

Bytecode
   |
   v
Hot method detected
   |
   v
JIT compiler
   |
   v
Native machine code

Then:

method call
   |
   v
native code

can execute much faster.

50. Hot Code

Suppose:

for (int i = 0; i < 1_000_000_000; i++) {
    calculate(i);
}

The JVM notices:

calculate()

is executed extremely frequently.

It becomes a candidate for JIT compilation.

This is why JIT is called:

Just-In-Time.

Compilation occurs while the application is running.

51. Tiered Compilation

HotSpot commonly uses multiple compilation levels.

Conceptually:

Bytecode
   |
Interpreter
   |
   +------> C1
   |
   +------> C2

C1

Faster compilation.

Useful for code that becomes warm quickly.

C2

More aggressive optimization.

Useful for very hot code.

52. Why Not Compile Everything Immediately?

Because compilation itself costs CPU and memory.

Suppose:

10,000 methods

but only:

50 methods

are heavily used.

Compiling all 10,000 would waste resources.

JIT focuses optimization effort on hot code.

53. JIT Profiling

The JVM collects runtime information such as:

  • method invocation frequency
  • branch behavior
  • type information
  • loop behavior

This runtime knowledge allows optimizations that static compilation may not know are safe.

This is one of the major reasons Java can be extremely fast.

54. Method Inlining

One of the most important JIT optimizations.

Suppose:

int add(int a, int b) {
    return a + b;
}

And:

int result = add(x, y);

The JIT may effectively turn this into:

int result = x + y;

Conceptually:

+-----------------------+
|      method call      |
+-----------------------+
            |
            v
+-----------------------+
|   inline method body  |
+-----------------------+
            |
            v
+-----------------------+
| optimize larger block |
+-----------------------+

Inlining can eliminate method-call overhead and expose more optimization opportunities.

55. Why Inlining Is Powerful

Suppose:

foo()
  |
  +--> bar()
          |
          +--> calculate()

Without inlining:

+-----+     +-----+     +-----------+
| foo | --> | bar | --> | calculate |
+-----+     +-----+     +-----------+

With inlining:

foo
 |
 +--> bar body
       |
       +--> calculate body

Now the optimizer can see the entire path.

This enables further optimizations.

56. Escape Analysis

This is an advanced but important concept.

Suppose:

Point create() {
    Point p = new Point(10, 20);
    return p;
}

The JVM analyzes:

Does p escape this method/thread?

If an object doesn't escape, the JVM may optimize its allocation.

Potential optimizations include:

  • scalar replacement
  • eliminating synchronization
  • reducing allocation

Important:

Escape analysis does not simply mean "objects are allocated on the stack."

That common explanation is misleading.

57. Scalar Replacement

Suppose:

Point p = new Point(10, 20);

int x = p.x;
int y = p.y;

If the object doesn't actually need to exist as an object, the JIT may conceptually replace:

Point object

with:

x = 10
y = 20

This can eliminate heap allocation.

58. Devirtualization

Consider:

interface Payment {
    void pay();
}

Then:

payment.pay();

Normally the JVM may not know exactly which implementation will execute.

But runtime profiling may show:

+-----+-------------------+
| 99% | CreditCardPayment |
+-----+-------------------+
+----+--------------+
| 1% | OtherPayment |
+----+--------------+

The JIT can optimize the common case.

This is related to:

speculative optimization.

59. Speculative Optimization

The JIT can optimize based on observed runtime behavior.

Example:

Observed:
method almost always receives type A

JIT:

optimize for A

But what if type B arrives?

The JVM can:

deoptimize
→ fall back to a safer execution path

This is called:

deoptimization

60. Deoptimization

Very important interview concept.

JIT optimization may depend on assumptions.

Example:

Assumption:
Only implementation A is observed.

Later:

Implementation B appears.

The optimized machine code may no longer be valid.

JVM can:

+---------------------------+
| invalidate optimized code |
+---------------------------+
              |
              v
+---------------------------+
|         deoptimize        |
+---------------------------+
              |
              v
+---------------------------+
|      continue safely      |
+---------------------------+

So JIT optimization is dynamic and adaptive.

61. Code Cache

Compiled native code needs memory.

The JVM maintains a code cache for generated machine code.

Conceptually:

Heap
Metaspace
Code Cache
Stacks

If the code cache becomes constrained, JIT compilation behavior can be affected.

This can matter during production performance investigations.

62. JVM Warmup

A Java application may not perform identically immediately after startup.

Initially:

Interpreter

Then:

+-----------------+
|    profiling    |
+-----------------+
         |
         v
+-----------------+
|  C1 compilation |
+-----------------+
         |
         v
+-----------------+
| C2 optimization |
+-----------------+

So performance can improve after warmup.

This matters for:

  • benchmarks
  • server startup
  • latency testing
  • performance comparisons

63. Why Microbenchmarks Are Dangerous

This is why you shouldn't benchmark Java like:

long start = System.nanoTime();

for (...) {
    method();
}

long end = System.nanoTime();

and assume the result is authoritative.

Issues include:

  • JIT warmup
  • dead-code elimination
  • constant folding
  • inlining
  • GC
  • CPU frequency changes
  • OS scheduling
  • caches

For serious JVM benchmarking:

Use JMH.

64. Dead Code Elimination

Suppose:

for (int i = 0; i < 1_000_000; i++) {
    int x = i * 2;
}

If x is never used, the JIT may determine the computation has no observable effect and remove it.

Therefore your benchmark may accidentally benchmark:

nothing

rather than:

i * 2

73. Allocation Rate

One of the most important production concepts.

Suppose your application allocates:

5 GB/sec

Even if objects die quickly, the GC has enormous work to do.

So GC behavior isn't only about:

heap size

It is also about:

allocation rate
object lifetime
live-set size

74. Live Set

Suppose:

Heap = 16 GB

but application actually keeps:

12 GB

alive.

That's very different from:

Heap = 16 GB
Live objects = 1 GB

A high live set can make collections expensive because the collector has much more live data to process.

75. Memory Leak in Java

Java can still have memory leaks.

Example:

static List<Object> cache =
    new ArrayList<>();

Suppose you continually add objects:

cache.add(new Object());

The GC can't collect them because:

GC Root
  |
  v
static cache
  |
  +--> object
  +--> object
  +--> object

They are still reachable.

Therefore:

GC prevents unreachable-object memory leaks, but it cannot fix accidentally retained reachable objects.

76. Common Java Memory Leak Patterns

Know these:

Static collections

static Map<Key, Object> cache;

Unbounded caches

cache grows forever

Listeners not removed

event source → listener

ThreadLocal misuse

ThreadLocal<LargeObject>

especially with long-lived thread pools.

ClassLoader leaks

Common in containers/redeployment environments.

77. ThreadLocal and Memory

Example:

private static final ThreadLocal<byte[]> DATA =
    new ThreadLocal<>();

If a thread pool thread remains alive and the value isn't removed appropriately, the referenced object can stay alive.

Best practice when appropriate:

try {
    DATA.set(largeObject);
    ...
} finally {
    DATA.remove();
}

This is particularly important when threads are reused.
