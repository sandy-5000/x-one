Yes, C does not have native language-level threads. It relies on operating-system threading APIs or external libraries to create and manage threads.

However, there is an important distinction.

1. Threading options in C

+----------------------------------+-----------------------------------+----------------------------+
| Threading mechanism              | Provided by                       | Type                       |
+----------------------------------+-----------------------------------+----------------------------+
| POSIX Threads (`pthread`)        | OS/POSIX API                      | OS-level threads           |
| Windows Threads (`CreateThread`) | Windows API                       | OS-level threads           |
| C11 Threads (`thrd_create`)      | C standard library implementation | Typically OS-level threads |
| OpenMP (`#pragma omp parallel`)  | Compiler + OpenMP runtime         | Typically OS-level threads |
| GNU Pth                          | External library                  | User-level threads         |
+----------------------------------+-----------------------------------+----------------------------+

2. What about C11 threads?

C11 introduced a standard threading API in `threads.h`.

#include <threads.h>
#include <stdio.h>

int worker(void *arg)
{
    printf("Worker thread\n");
    return 0;
}

int main(void)
{
    thrd_t thread;

    thrd_create(&thread, worker, NULL);
    thrd_join(thread, NULL);

    return 0;
}

Here:

  • thrd_create() creates a thread.
  • thrd_join() waits for it to finish.
  • The C standard defines the interface, but does not require a particular implementation strategy for threads.
  • On mainstream systems, the implementation typically uses OS-level threads.

Note that C11 threading support is not available in every C standard library.

3. Can C have user-level threads?

Yes. C can implement user-level threading through libraries or custom runtime code.

User-level threads are managed by a runtime in user space rather than being individually scheduled by the OS.

For example:

  • OS-level threads: The OS schedules each thread independently.
  • User-level threads: A runtime schedules multiple logical threads, potentially across one or more OS threads.
  • Fibers: Cooperative execution units that explicitly yield control.
  • Coroutines: Functions that can suspend and resume execution; these can be implemented in C using libraries or custom code.

C itself does not provide built-in coroutine syntax or a native user-level thread scheduler.

4. Comparison with other languages

+----------+------------------------+--------------------------------------------+
| Language | Standard threading API | User-level concurrency                     |
+----------+------------------------+--------------------------------------------+
| C        | C11 ``threads.h``      | Libraries/custom runtime                   |
| C++      | `std::thread`          | Coroutines and libraries                   |
| Java     | `Thread`               | Virtual threads                            |
| Go       | `go` keyword           | Goroutines managed by the Go runtime       |
| Rust     | `std::thread`          | Async tasks through runtimes such as Tokio |
+----------+------------------------+--------------------------------------------+

Key distinction: C11 threads and C++ std::thread provide language-standard interfaces, but that doesn't mean the threads are implemented by the language runtime itself.

If you're implementing a database in C, you can use pthread for OS threads or build a user-level task scheduler if you need lightweight concurrency.

To create a user-level threading library in C, you need to implement a runtime that creates, schedules, pauses, and resumes multiple logical threads without creating a separate OS thread for each one.

You can build this entirely in C using operating-system primitives and CPU context-switching mechanisms.

1. Understand the architecture

Suppose you want to create this API:

#include "uthread.h"

void task1(void *arg)
{
    /* Do some work */
}

void task2(void *arg)
{
    /* Do some work */
}

int main(void)
{
    uthread_init();

    uthread_create(task1, NULL);
    uthread_create(task2, NULL);

    uthread_run();

    uthread_destroy();
    return 0;
}

Your library would expose a simple API, while its implementation handles scheduling and execution.

The architecture looks like this:

Application
    |
    v
 User Thread Library
    |
    +-- Thread Creation
    |
    +-- Thread Context Management
    |
    +-- Scheduler
    |
    +-- Ready Queue
    |
    +-- Context Switching
    |
    v
 Operating System
    |
    v
 One or more OS threads

In the simplest implementation, all user-level threads run on one OS thread.

The OS knows about the underlying OS thread, but your library manages the logical threads running on it.

2. Decide how to implement context switching

The most important part is switching execution from one user-level thread to another.

Each thread needs its own:

  • Stack
  • CPU execution context
  • State (ready, running, blocked, or terminated)
  • Entry function and arguments

For example, imagine two threads:

OS Thread
    |
    +-- User Thread A
    |      Stack A
    |      Execution Context A
    |
    +-- User Thread B
           Stack B
           Execution Context B

Only one user-level thread executes at a time on this OS thread. When A yields, the library saves A's execution context and restores B's context.

There are three main approaches.

+----------------------------+-----------------------------------------------------------------------------------------------------------+------------+
| Approach                   | How it works                                                                                              | Complexity |
+----------------------------+-----------------------------------------------------------------------------------------------------------+------------+
| `ucontext`                 | Uses system context APIs to save and restore execution contexts                                           | Low        |
| `setjmp` / `longjmp`       | Saves and restores execution state, with significant limitations for building independent stacks portably | Medium     |
| Assembly context switching | Saves and restores registers and stack pointers directly                                                  | High       |
+----------------------------+-----------------------------------------------------------------------------------------------------------+------------+

Recommendation: Start with ucontext on Linux to understand the design, then implement your own assembly context-switching mechanism if you want to build a more portable, low-level library.

ucontext is a historical POSIX interface that is not part of modern POSIX standards, so it is useful for experimentation but not ideal as a universal production dependency.

3. Implement the thread data structure

Each user-level thread needs a control block.

Create uthread.h:

#ifndef UTHREAD_H
#define UTHREAD_H

typedef void (*uthread_fn)(void *);

typedef unsigned long uthread_id;

int uthread_init(void);

uthread_id uthread_create(uthread_fn fn, void *arg);

void uthread_yield(void);

void uthread_run(void);

void uthread_destroy(void);

#endif

Internally, you could represent each thread as follows:

typedef enum
{
    UTHREAD_READY,
    UTHREAD_RUNNING,
    UTHREAD_BLOCKED,
    UTHREAD_TERMINATED
} uthread_state;

typedef struct
{
    uthread_id id;
    uthread_state state;

    void *stack;
    size_t stack_size;

    uthread_fn function;
    void *argument;

    /* Execution context goes here. */
} uthread;

The execution context will depend on your chosen context-switching mechanism.

The scheduler maintains these structures and selects which thread should run next.

4. Implement thread creation

When the application calls:

uthread_create(task1, NULL);

Your library should:

  1. Allocate a thread control block.
  2. Allocate a stack for the new thread.
  3. Initialize its execution context.
  4. Configure the context to start at a library-controlled entry function.
  5. Add the thread to the ready queue.
  6. Return its ID.

A typical stack allocation might be:

#define UTHREAD_STACK_SIZE (64 * 1024)

void *stack = malloc(UTHREAD_STACK_SIZE);

if (stack == NULL)
{
    return 0;
}

This is only the stack allocation step, not a complete thread implementation. Production-quality code should also consider stack alignment, guard pages, cleanup, and platform-specific context requirements.

Why does every thread need a separate stack?

Consider these functions:

void task1(void *arg)
{
    int value = 10;

    uthread_yield();

    value += 5;
}

When task1() yields, its local variable value must remain available when the thread resumes.

Its stack preserves the function's local variables, return addresses, and other stack-related execution state.

Without a separate stack for each independently suspended thread, ordinary function calls could overwrite one another's execution state.

5. Implement context switching

Suppose thread A is running and calls:

uthread_yield();

Your library must:

  1. Save A's current execution context.
  2. Mark A as ready.
  3. Select another ready thread, B.
  4. Mark B as running.
  5. Restore B's execution context.
  6. Resume B from where it previously yielded, or start it for the first time.

With ucontext, the underlying operations involve functions such as:

  • getcontext() — capture a context.
  • makecontext() — configure a context to begin execution at a function.
  • swapcontext() — save the current context and activate another.
  • setcontext() — activate a saved context without saving the current one.

A simplified conceptual implementation is:

void uthread_yield(void)
{
    uthread *current = scheduler_current_thread();

    current->state = UTHREAD_READY;

    scheduler_enqueue(current);

    uthread *next = scheduler_next_thread();

    next->state = UTHREAD_RUNNING;

    scheduler_switch_context(current, next);
}

The functions beginning with scheduler_ are internal helpers you would implement.

Important: This is pseudocode, not a complete implementation. A real scheduler must handle empty queues, terminated threads, repeated yields, and the transition between the scheduler context and thread contexts.

6. Build the scheduler

Start with a cooperative round-robin scheduler.

Suppose you create three user-level threads:

uthread_create(task1, NULL);
uthread_create(task2, NULL);
uthread_create(task3, NULL);

Your scheduler might execute them as follows:

Ready Queue: [A, B, C]

Run A
A calls uthread_yield()
Ready Queue: [B, C, A]

Run B
B calls uthread_yield()
Ready Queue: [C, A, B]

Run C
C calls uthread_yield()
Ready Queue: [A, B, C]

Each thread explicitly gives up control by calling uthread_yield().

This is called cooperative scheduling.

One major limitation: if thread A enters an infinite loop without yielding, threads B and C cannot run on that OS thread.

For example:

void task1(void *arg)
{
    while (1)
    {
        /* Never yields. */
    }
}

A cooperative scheduler cannot preempt this thread automatically.

You can investigate preemptive scheduling later, but it requires additional mechanisms and careful handling of asynchronous interruption.

7. Handle thread termination

A thread should not return directly into arbitrary memory or fall through into another thread's execution context.

Instead, have every new thread begin through a wrapper:

static void uthread_entry(void)
{
    uthread *current = scheduler_current_thread();

    current->function(current->argument);

    current->state = UTHREAD_TERMINATED;

    scheduler_switch_to_scheduler();
}

This is conceptual pseudocode; the actual entry function must be compatible with the context API you choose.

When a thread terminates, the scheduler can:

  • Remove it from the runnable set.
  • Record its exit state.
  • Reclaim its resources when safe.

Do not free a thread's stack while that stack is still executing. Switch to the scheduler's stack before reclaiming it.

8. What about blocking operations?

This is one of the most important design decisions.

Imagine a user-level thread executes:

read(socket_fd, buffer, sizeof(buffer));

If the socket is blocking and no data is available, the OS may block the entire underlying OS thread.

Consequently, all user-level threads scheduled on that OS thread stop making progress.

To avoid this, a more advanced library can use:

  • Nonblocking sockets.
  • epoll on Linux.
  • kqueue on BSD-derived systems and macOS.
  • A runtime-managed event loop.
  • A blocked-thread queue.

For example:

User Thread A
      |
      v
Nonblocking socket read
      |
      +-- Data available --> Continue A
      |
      +-- EAGAIN ---------> Suspend A
                                 |
                                 v
                           Event Loop
                                 |
                                 v
                         Socket becomes ready
                                 |
                                 v
                         Resume A

This is how you can eventually evolve a basic user-level threading library into a runtime suitable for network servers.

10. Recommended implementation milestones

Build the library incrementally:

+-----------+-----------------------------+----------------------------------------------------------+
| Milestone | Feature                     | What it proves                                           |
+-----------+-----------------------------+----------------------------------------------------------+
| 1         | Thread control blocks       | Thread metadata is managed correctly                     |
| 2         | Independent stacks          | Threads can maintain separate execution state            |
| 3         | Context switching           | Execution can move between threads                       |
| 4         | Cooperative scheduler       | Threads can yield and resume                             |
| 5         | Thread termination          | Completed threads can be cleaned up safely               |
| 6         | Synchronization primitives  | Threads can coordinate access to shared data             |
| 7         | Nonblocking I/O integration | Threads can suspend while waiting for external events    |
| 8         | Multiple OS threads         | User-level threads can execute across multiple CPU cores |
+-----------+-----------------------------+----------------------------------------------------------+

Start with milestones 1–5 before implementing synchronization, I/O integration, or multicore execution.

One final distinction

Your first implementation would be a many-to-one threading model:

User Threads: A, B, C, D
          \   |   |   /
           One OS Thread
                 |
                 v
                 OS

If you later create a pool of OS threads and schedule user-level threads across them, you move toward a many-to-many threading model.

That requires additional synchronization because multiple user-level threads may execute simultaneously on different CPU cores.

For a first implementation, a cooperative scheduler using one OS thread and separate stacks is the simplest design to understand and validate.

For learning purposes, the simplest way to implement context switching in C on Linux is to use ucontext first, then replace it with your own assembly code to understand what actually happens at the CPU level.

A context switch essentially saves the current execution state and restores another execution state, including its stack pointer and instruction location.

I'll show you how to implement it yourself using x86-64 assembly.

1. Understand what needs to be switched

Consider two functions:

void task_a(void)
{
    while (1)
    {
        printf("A\n");
        yield();
    }
}

void task_b(void)
{
    while (1)
    {
        printf("B\n");
        yield();
    }
}

You want the output to alternate:

A
B
A
B
A
B

When task_a() calls yield(), it must suspend at that exact point. When resumed, it should continue executing after the call to yield().

To accomplish this, you need to preserve:

  • Stack pointer (RSP): Where the current stack is located.
  • Instruction pointer (RIP): Where execution should continue.
  • Callee-saved registers: Registers that must retain their values across function calls according to the calling convention.

You don't necessarily need to save every CPU register manually. A function-call-based context switch can rely on the ABI to preserve the registers required by the calling convention.

2. Create the project

Use two files:

+-----------+
|  uthread/ |
+-----------+
      |
      v
+-----------+
|  ├ main.c |
+-----------+
      |
      v
+-----------+
| context.S |
+-----------+

This example targets Linux x86-64 using the System V AMD64 ABI, which is commonly used by Linux distributions on Intel and AMD processors.

It is not portable to ARM64 or Windows without changes.

3. Implement the context-switching function in assembly

Create context.S:

.text

.globl context_switch

# void context_switch(void **old_rsp, void *new_rsp)
#
# RDI = address where the old RSP will be stored
# RSI = new RSP to load

context_switch:
    # Save callee-saved registers on the current stack.
    pushq %rbp
    pushq %rbx
    pushq %r12
    pushq %r13
    pushq %r14
    pushq %r15

    # Save the current stack pointer.
    movq %rsp, (%rdi)

    # Switch to the new stack.
    movq %rsi, %rsp

    # Restore the destination context's registers.
    popq %r15
    popq %r14
    popq %r13
    popq %r12
    popq %rbx
    popq %rbp

    # Return to the destination context.
    ret

How does this work?

Suppose context A switches to context B.

Step 1: Save A's registers

The pushq instructions save the callee-saved registers on A's stack.

Step 2: Save A's stack pointer

movq %rsp, (%rdi)

This stores A's current stack pointer in the memory location pointed to by old_rsp.

Step 3: Load B's stack pointer

movq %rsi, %rsp

The CPU now uses B's stack.

Step 4: Restore B's registers

The popq instructions restore the registers previously saved on B's stack.

Step 5: Resume B

ret

The ret instruction pops a return address from B's stack and continues execution there.

That last step is the key: the saved stack must contain a valid return address at the correct location.

For an existing context, that return address was placed there by the earlier call to context_switch().

For a new context, you must initialize its stack so that the first ret transfers execution to a function you choose.

4. Initialize a new thread's stack

For an existing thread, you already have a saved stack pointer.

For a new thread, you must construct an initial stack frame that matches the layout expected by context_switch().

After switching stacks, the assembly function executes six popq instructions followed by ret.

Therefore, the initial stack must look like this:

Higher memory addresses
        |
        v
+------------------------+
| Initial function addr  | <-- consumed by ret
+------------------------+
| Initial RBP            |
+------------------------+
| Initial RBX            |
+------------------------+
| Initial R12            |
+------------------------+
| Initial R13            |
+------------------------+
| Initial R14            |
+------------------------+
| Initial R15            | <-- new RSP
+------------------------+
        |
        v
Lower memory addresses

The initial %rsp must point at the saved R15 slot.

Your C code can prepare this stack layout manually.

5. Implement the C side

Create main.c:

#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>

#define STACK_SIZE (64 * 1024)

typedef void (*task_fn)(void);

extern void context_switch(void **old_rsp, void *new_rsp);

typedef struct
{
    void *rsp;
    void *stack;
    task_fn function;
} task;

static task task_a;
static task task_b;

static void task_entry(void)
{
    /*
     * This entry function is reached by the initial context's ret.
     * The scheduler must arrange for the task function to be invoked.
     */
    task *current = NULL;

    /* We'll replace this placeholder in the next section. */
    (void)current;
}

Rather than introducing a scheduler immediately, let's make the example smaller and demonstrate the context switch itself.

The complete example below uses two contexts: the original main() context and one newly initialized context.

#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>

#define STACK_SIZE (64 * 1024)

extern void context_switch(void **old_rsp, void *new_rsp);

static void *main_rsp;
static void *worker_rsp;
static void *worker_stack;

static void worker(void)
{
    printf("Worker: first execution\n");

    context_switch(&worker_rsp, main_rsp);

    printf("Worker: resumed execution\n");

    context_switch(&worker_rsp, main_rsp);

    printf("Worker: finished\n");

    /* Never return into an invalid caller. */
    abort();
}

static void initialize_worker(void)
{
    worker_stack = malloc(STACK_SIZE);

    if (worker_stack == NULL)
    {
        perror("malloc");
        exit(EXIT_FAILURE);
    }

    /*
     * Construct the initial stack frame expected by context_switch().
     * x86-64 System V ABI: keep the stack 16-byte aligned before
     * entering the worker function.
     */
    uintptr_t *sp = (uintptr_t *)
        (((uintptr_t)worker_stack + STACK_SIZE) & ~(uintptr_t)0xF);

    *--sp = (uintptr_t)worker; /* Return address */
    *--sp = 0;                 /* RBP */
    *--sp = 0;                 /* RBX */
    *--sp = 0;                 /* R12 */
    *--sp = 0;                 /* R13 */
    *--sp = 0;                 /* R14 */
    *--sp = 0;                 /* R15 */

    worker_rsp = sp;
}

int main(void)
{
    initialize_worker();

    printf("Main: switching to worker\n");
    context_switch(&main_rsp, worker_rsp);

    printf("Main: worker yielded\n");
    context_switch(&main_rsp, worker_rsp);

    printf("Main: worker yielded again\n");
    context_switch(&main_rsp, worker_rsp);

    printf("Main: done\n");

    free(worker_stack);
    return 0;
}

Save the assembly implementation from the previous section as context.S.

Compile and run:

gcc -Wall -Wextra -O0 main.c context.S -o context_demo
./context_demo

Expected output:

Main: switching to worker
Worker: first execution
Main: worker yielded
Worker: resumed execution
Main: worker yielded again
Worker: finished
Aborted

Important correction: The example above calls abort() at the end of worker(), so it intentionally aborts rather than completing normally. For a clean exit, the worker must switch back to main() after printing Worker: finished, and main() must not switch to the worker again. The stack alignment and startup layout should also be validated for the compiler and ABI you're using.

6. What you should learn from this

The central mechanism is remarkably small:

movq %rsp, (%rdi)
movq %rsi, %rsp

The remaining instructions preserve registers and resume execution correctly.

However, there are three distinct concepts:

+-----------------------+-----------------------------------------------------+
| Concept               | Purpose                                             |
+-----------------------+-----------------------------------------------------+
| Stack switching       | Gives each thread its own function-call stack       |
| Register preservation | Keeps the suspended thread's execution state intact |
| Control transfer      | Resumes at the saved return address                 |
+-----------------------+-----------------------------------------------------+

This example uses cooperative context switching: a thread switches only when it explicitly calls context_switch().

A production runtime would need additional handling for stack alignment, stack overflow, thread termination, signals, floating-point/SIMD state, and other ABI requirements.

For your learning project, the next useful step is to add a thread-control structure containing each thread's stack pointer and stack allocation, then implement yield() to switch between two such structures.

My recommendation

Since your goal is to learn how threading works internally, follow these steps.

Step 1: Start with ucontext

Learn how to:

  • Allocate a separate stack for each thread.
  • Initialize an execution context.
  • Switch between contexts.
  • Implement yield().
  • Build a round-robin scheduler.

You can implement all of this in C without writing assembly.

Step 2: Understand what happens during a context switch

Learn these concepts without necessarily writing assembly:

  • Stack pointer (RSP)
  • Instruction pointer (RIP)
  • CPU registers
  • Function calling conventions
  • Stack frames
  • Return addresses

Step 3: Learn assembly when you want to implement the mechanism yourself

You only need a small subset of x86-64 assembly to implement a basic cooperative context switch. You don't need to master the entire instruction set.

One important distinction

Using ucontext means you're learning to build a threading runtime, but the operating system or system libraries still provide the underlying execution mechanisms.

Writing your own assembly context switch lets you learn how to implement the low-level switching mechanism itself.

For your goal, start with ucontext and move to assembly later. This lets you understand scheduling and thread management before dealing with architecture-specific details.

context_switch() is implemented in the context.S assembly file, not in main.c.

You declare it in C using extern so the compiler knows the function exists elsewhere.

1. main.c — function declaration

extern void context_switch(void **old_rsp, void *new_rsp);

This tells the C compiler that another compiled file provides this function.

2. context.S — actual implementation

Create a file named context.S with this code:

.text

.globl context_switch

context_switch:
    pushq %rbp
    pushq %rbx
    pushq %r12
    pushq %r13
    pushq %r14
    pushq %r15

    movq %rsp, (%rdi)
    movq %rsi, %rsp

    popq %r15
    popq %r14
    popq %r13
    popq %r12
    popq %rbx
    popq %rbp

    ret

Here, .globl context_switch makes the symbol visible to the linker, allowing C code to call it.

3. Compile both files together

Your project structure:

+-----------+
|  project/ |
+-----------+
      |
      v
+-----------+
|  ├ main.c |
+-----------+
      |
      v
+-----------+
| context.S |
+-----------+

Compile them together:

gcc -Wall -Wextra -O0 main.c context.S -o context_demo

Run:

./context_demo

How the files work together:

  1. The C compiler compiles main.c and sees the external function declaration.
  2. The assembler translates context.S into machine code.
  3. The linker connects the call in main.c to the implementation in context.S.

The .S extension tells GCC to preprocess and assemble the file. This example is specifically for Linux x86-64 using the System V ABI.
