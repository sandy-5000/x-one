Docker Compose deep dive — Apple IC4 preparation

Lesson 10 of the main course introduced Compose as a convenient way to run several containers. This lesson goes further: what Compose actually does against the Docker Engine, where its guarantees end, and how to reason about failures in a multi-service setup.

The goal is to be able to answer, without guessing:

  • What exactly happens when I run docker compose up?
  • Why did my container get recreated (or not) after I edited the file?
  • Why can api not reach db even though both are "up"?
  • When is Compose the right tool, and when is it the wrong one?

1. What Compose actually is

Compose is a client-side tool. It reads a YAML file, computes the desired set of networks, volumes, and containers, and then makes ordinary Docker Engine API calls to create them.

+--------------------+      +---------------------+      +-------------------+
|   compose.yaml     | ---> |   docker compose    | ---> |   Docker Engine   |
|  (desired state)   |      |  (client, plugin)   |      |  (dockerd + API)  |
+--------------------+      +---------------------+      +-------------------+
                                                                   |
                                                                   v
                                                         +-------------------+
                                                         | containerd / runc |
                                                         +-------------------+

Key consequences:

  • There is no Compose daemon and no controller running after up returns. Nothing continuously reconciles state.
  • If a container dies, the Engine's restart policy restarts it — not Compose.
  • If the host dies, nothing reschedules your services elsewhere. Compose is a single-host tool.

Compose V1 versus V2

  • V1 — docker-compose (hyphen), written in Python. End of life since mid-2023.
  • V2 — docker compose (space), written in Go, shipped as a Docker CLI plugin. Use this.

The file format is the Compose Specification. The old top-level version: key is obsolete; V2 ignores it and prints a warning.

How Compose tracks what it created

Compose finds "its" resources through labels, not through a database:

docker inspect shop-api-1 --format '{{json .Config.Labels}}'

You will see labels such as:

  • com.docker.compose.project — the project name
  • com.docker.compose.service — the service name
  • com.docker.compose.container-number — replica index
  • com.docker.compose.config-hash — a hash of the service's resolved configuration

The config hash is how Compose decides whether a container must be recreated. If the hash of the new configuration differs from the label on the running container, up recreates it. If it matches, the container is left alone.

2. Mental model: project, services, containers

+-------------------------------------------------------------------+
| Project: shop  (from directory name, -p, or top-level name:)      |
|                                                                   |
|   Service: web     Service: api              Service: db          |
|   +----------+     +----------+----------+   +----------+         |
|   |  web-1   |     |  api-1   |  api-2   |   |   db-1   |         |
|   +----------+     +----------+----------+   +----------+         |
|                                                                   |
|   Network: shop_default        Volume: shop_db-data               |
+-------------------------------------------------------------------+
  • Project — the namespace. Its name prefixes every resource. Set it with the top-level name: key, -p, or COMPOSE_PROJECT_NAME; otherwise it defaults to the directory name.
  • Service — a template for one or more identical containers.
  • Container — named <project>-<service>-<index>, for example shop-api-2.

Two copies of the same directory with the same project name will fight over the same containers. Always set an explicit name: in shared repositories.

3. Anatomy of a realistic compose.yaml

name: shop

services:
  web:
    build:
      context: ./web
      target: runtime
    ports:
      - "8080:80"
    depends_on:
      api:
        condition: service_healthy
    networks: [frontend]

  api:
    build: ./api
    environment:
      DATABASE_URL: postgres://app@db:5432/shop
      LOG_LEVEL: ${LOG_LEVEL:-info}
    secrets: [db_password]
    depends_on:
      db:
        condition: service_healthy
        restart: true
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://localhost:3000/health"]
      interval: 10s
      timeout: 3s
      retries: 3
      start_period: 20s
    deploy:
      resources:
        limits:
          cpus: "1.0"
          memory: 512M
    stop_grace_period: 20s
    init: true
    networks: [frontend, backend]

  db:
    image: postgres:16
    environment:
      POSTGRES_USER: app
      POSTGRES_DB: shop
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password
    secrets: [db_password]
    volumes:
      - db-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d shop"]
      interval: 5s
      timeout: 3s
      retries: 10
    networks: [backend]

  adminer:
    image: adminer
    profiles: [debug]
    ports:
      - "8081:8080"
    networks: [backend]

networks:
  frontend:
  backend:
    internal: true

volumes:
  db-data:

secrets:
  db_password:
    file: ./secrets/db_password.txt

Things worth noticing:

  • db is on an internal network, so it has no route to the outside world and is unreachable from web.
  • api sits on both networks and is the only bridge between them.
  • The password never appears in environment; it is mounted as a file at /run/secrets/db_password.
  • adminer only starts when you ask for the debug profile.
  • init: true runs a tiny init process as PID 1 so signals are forwarded and zombies reaped.

4. Networking

The default network

Without a networks: section, Compose creates one bridge network called <project>_default and attaches every service to it.

Service discovery

Every container uses Docker's embedded DNS server at 127.0.0.11. On a user-defined network:

  • The service name (db) resolves to the IPs of all containers of that service.
  • The container name (shop-db-1) resolves to that one container.
  • Extra names can be added with aliases: under a service's network entry.

Inspect it from inside a container:

docker compose exec api cat /etc/resolv.conf
docker compose exec api getent hosts db

ports versus expose

  • ports: ["8080:80"] publishes to the host. Anything that can reach the host can reach it.
  • Containers on the same network do not need ports to talk to each other. They use the container port directly: db:5432.
  • expose: is documentation only; it does not publish anything.

A very common mistake is publishing the database port "so the API can reach it". The API never needed it, and now the database is exposed on the host.

Isolating tiers with multiple networks

+---------+   frontend   +---------+   backend    +---------+
|   web   | -----------> |   api   | -----------> |   db    |
+---------+              +---------+  (internal)  +---------+

web and api share frontend; api and db share backend. web cannot resolve or reach db at all, because they share no network.

Bind address for published ports

"8080:80" binds to all host interfaces. For local-only tools, bind explicitly:

ports:
  - "127.0.0.1:8081:8080"

Also remember that Docker inserts its own iptables rules, so a host firewall such as ufw may not block published ports the way you expect.

5. Startup order and health

The short form only orders creation

depends_on: [db]

This only guarantees that the db container is started before api. It does not wait for Postgres to accept connections.

The long form waits on a condition

  • service_started — same as the short form.
  • service_healthy — waits until the dependency's health check reports healthy.
  • service_completed_successfully — waits until a one-shot container (for example, a migration job) exits with code 0.
  • restart: true — if Compose restarts the dependency, it also restarts this service.

A typical pattern with a migration step:

services:
  migrate:
    build: ./api
    command: ["npm", "run", "migrate"]
    depends_on:
      db:
        condition: service_healthy

  api:
    build: ./api
    depends_on:
      migrate:
        condition: service_completed_successfully

Why your application must still retry

depends_on only applies at startup through Compose. It does nothing when:

  • the database restarts later,
  • the network blips,
  • a container is restarted by the Engine's restart policy.

Ordering is a convenience for local startup. Resilience — retries with backoff, timeouts, readiness checks — belongs in the application.

6. Configuration and environment

There are two completely different mechanisms that both involve "env files". Confusing them is one of the most common Compose bugs.

Interpolation: the .env file

A .env file next to compose.yaml provides values for ${VAR} substitution inside the YAML. It does not automatically inject anything into containers.

image: myapp:${TAG:-latest}

Useful syntax:

  • ${VAR:-default} — use default if unset or empty.
  • ${VAR-default} — use default only if unset.
  • ${VAR:?message} — fail with an error if unset or empty.
  • $$ — a literal $, for example inside a shell command.

Container environment: env_file and environment

  • env_file: [api.env] — reads the file and sets those variables inside the container.
  • environment: — sets variables inside the container directly.

Precedence

From highest to lowest for a container's environment:

  1. docker compose run -e VAR=...
  2. environment: in the file (after interpolation)
  3. env_file:
  4. ENV in the image's Dockerfile

Always render the final configuration

docker compose config

This prints the fully merged, interpolated model that Compose will actually apply. When something behaves unexpectedly, check this before anything else.

7. Storage

Three kinds of mounts

  • Named volume (db-data:/var/lib/postgresql/data) — managed by Docker, created as <project>_db-data, survives down.
  • Bind mount (./src:/app/src) — a host path. Ideal for development, risky for production.
  • tmpfs — in-memory, disappears when the container stops. Good for scratch data and secrets.

Data loss traps

  • docker compose down keeps named volumes.
  • docker compose down -v deletes named volumes declared in the file. On a database, that is your data.
  • Renaming the project changes the volume name. The old data is still there, but the new project starts with an empty volume.

Permission problems with bind mounts

Files created inside the container belong to the container's UID. If the container runs as UID 1000 but the host directory belongs to UID 1001, you get EACCES. Fix it by aligning UIDs (user: "1000:1000") or adjusting ownership — not by running everything as root.

External volumes

volumes:
  db-data:
    external: true
    name: prod_db_data

Compose will not create or delete an external volume; it must already exist.

8. Multiple files and environments

Override files

If both exist, Compose automatically merges:

  • compose.yaml
  • compose.override.yaml

The usual pattern is production-like settings in the base file and development settings (bind mounts, debug ports) in the override.

Explicit file lists

docker compose -f compose.yaml -f compose.prod.yaml up -d

Later files override earlier ones. Merge rules worth knowing:

  • Single values (image, command) are replaced.
  • ports, expose, dns are appended.
  • environment and labels are merged by key.

include

include:
  - ../shared/observability.yaml

include pulls in a complete Compose application, with its paths resolved relative to its own location. It is the cleanest way to share infrastructure between projects.

Profiles

docker compose --profile debug up -d
COMPOSE_PROFILES=debug,tools docker compose up -d

Services without a profiles: key always start. Services with one only start when that profile is enabled.

9. Development workflow

Build integration

docker compose build api
docker compose up -d --build
docker compose build --no-cache api

Compose uses BuildKit. target:, args:, cache_from:, and secrets: under build: work as they do with docker build.

File watching

services:
  api:
    build: ./api
    develop:
      watch:
        - action: sync
          path: ./api/src
          target: /app/src
        - action: rebuild
          path: ./api/package.json
docker compose watch
  • sync copies changed files into the running container.
  • rebuild rebuilds the image and recreates the container.
  • sync+restart syncs, then restarts the container.

Everyday commands

docker compose ps
docker compose logs -f --tail=100 api
docker compose exec api sh
docker compose run --rm api npm test
docker compose top
docker compose events

exec enters a running container. run creates a new one-off container for the service, which is ideal for tests and admin tasks.

10. Lifecycle commands — what they really do

docker compose up

  1. Loads and merges the files, then interpolates variables.
  2. Creates networks and volumes that do not exist yet.
  3. Builds or pulls images as needed.
  4. For each service, in dependency order, compares the config hash: no container means create, a changed hash means recreate, an unchanged hash means leave it running.
  5. Starts containers and waits on depends_on conditions.

Use --force-recreate to recreate regardless of the hash, and --no-recreate to never recreate.

The others

  • stop — stops containers, keeps everything.
  • start — starts existing containers, does not apply config changes.
  • restart — restarts containers, does not apply config changes.
  • down — stops and removes containers and networks. Volumes stay unless -v.
  • down --rmi local — also removes images that Compose built.

Edited the file and nothing changed? You ran restart. Run up -d instead.

Graceful shutdown

On stop or down, Docker sends SIGTERM (or stop_signal) to PID 1, waits stop_grace_period (default 10s), then sends SIGKILL.

The application only receives SIGTERM if it is PID 1 or something forwards the signal. A shell-form command such as CMD npm start runs under /bin/sh -c, which may not forward signals. Use exec-form commands and init: true.

11. Scaling, and where Compose stops

docker compose up -d --scale api=3

This works only if the service has no fixed host port. Three containers cannot all bind host port 3000. Either publish a range ("3000-3002:3000"), or put a reverse proxy in front and let it resolve api through DNS.

Compose honours deploy.replicas and deploy.resources.limits, but it is still one host:

  • no rescheduling when the host fails,
  • no rolling updates with automatic rollback,
  • no cross-host networking.

Where Compose fits

  • Good fit — local development, CI integration tests, demos, small single-host internal tools.
  • Poor fit — anything that needs high availability, multi-host scheduling, or zero-downtime deploys. That is Swarm or Kubernetes territory.

12. Debugging playbook

Scenario A — "api cannot connect to db"

  1. docker compose ps — is db running and healthy?
  2. docker compose config — are both services on a shared network?
  3. docker compose exec api getent hosts db — does DNS resolve?
  4. Is the connection string using localhost? Inside api, localhost is api itself, not the database.
  5. Is the API connecting before Postgres is ready? Check health conditions and retry logic.

Scenario B — "my change was not applied"

  • Was it a restart instead of up -d?
  • Was it a code change that needs --build?
  • Is a stale override file merging in? Check docker compose config.

Scenario C — "the database is empty after a deploy"

  • Did someone run down -v?
  • Did the project name change, creating a new volume? Compare docker volume ls.

Scenario D — "containers take 10 seconds to stop"

The process is not handling SIGTERM, so Docker waits for the grace period and kills it. Check for shell-form commands and missing init: true.

13. Hands-on labs

Lab A — Observe the config hash

docker compose up -d
docker inspect shop-api-1 --format '{{index .Config.Labels "com.docker.compose.config-hash"}}'
# change LOG_LEVEL in compose.yaml
docker compose up -d
docker inspect shop-api-1 --format '{{index .Config.Labels "com.docker.compose.config-hash"}}'

Confirm that only api was recreated, and explain why.

Lab B — Prove network isolation

docker compose exec web getent hosts db || echo "web cannot see db"
docker compose exec api getent hosts db

Lab C — Break startup ordering

Remove the condition: service_healthy from api, restart the stack from scratch, and watch the API logs. Then add retry logic to the application instead of relying on ordering.

Lab D — Graceful shutdown

Run a container whose process ignores SIGTERM, time docker compose stop, then add init: true or fix the signal handling and time it again.

14. Interview questions with model answers

Does Compose keep my services running?

No. Compose applies the desired state once and exits. The Docker Engine's restart policy restarts crashed containers. Nothing moves them to another host.

How does Compose know whether to recreate a container?

It stores a hash of each service's resolved configuration as a label on the container. On up, it recomputes the hash and recreates the container only when the hashes differ.

What is the difference between .env and env_file?

.env feeds variable interpolation into the YAML itself. env_file injects variables into the container's environment. A value in .env never reaches the container unless the YAML references it.

Is depends_on enough to make a service resilient to a database restart?

No. It only orders startup. The application needs retries, timeouts, and health-aware connection handling.

When would you not use Compose?

When you need multiple hosts, automatic rescheduling, rolling updates with rollback, or high availability. Then you would use Swarm or Kubernetes.
