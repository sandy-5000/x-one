3. ExecutorService

One of the most important things to learn.

Instead of manually creating threads:

Thread t = new Thread(() -> {
    // work
});

t.start();

use an executor:

ExecutorService executor =
        Executors.newFixedThreadPool(10);

executor.submit(() -> {
    System.out.println("Running task");
});

executor.shutdown();

The executor manages worker threads for you.

4. Why thread pools exist

Creating a thread for every request is expensive.

Suppose:

10,000 requests

and you create:

10,000 threads

You have huge overhead.

Instead:

+-------------------+
|    10,000 tasks   |
+-------------------+
          |
          v
+-------------------+
|         ▼         |
+-------------------+
          |
          v
+-------------------+
|    Thread Pool    |
+-------------------+
          |
          v
+-------------------+
| T1   T2   T3   T4 |
+-------------------+

Tasks wait in a queue.

16. CAS — Compare And Swap

A fundamental concurrency concept.

Conceptually:

if currentValue == expectedValue
       update
else
       fail

Example:

AtomicInteger value = new AtomicInteger(10);

boolean success =
    value.compareAndSet(10, 20);

If value is still 10:

10 → 20

Otherwise:

no update

This is the basis of many lock-free algorithms.

18. LongAdder

Understand why LongAdder exists.

With huge concurrency:

AtomicLong

can experience contention because many threads update the same atomic variable.

LongAdder spreads updates across cells and combines them when reading.

LongAdder counter = new LongAdder();

counter.increment();

long value = counter.sum();

Good for high-contention statistics/counters.

19. AtomicReference

Useful when the shared object itself must change atomically.

AtomicReference<State> state =
        new AtomicReference<>(initialState);

Then:

state.compareAndSet(oldState, newState);

This becomes useful when implementing a rate limiter state machine.

20. volatile

A very commonly misunderstood keyword.

private volatile boolean running = true;

volatile provides visibility guarantees.

It does not make compound operations atomic.

This is unsafe:

volatile int count;

count++;

because:

read
increment
write

is still multiple operations.

21. Happens-before

You need a solid conceptual understanding.

The Java Memory Model defines relationships that guarantee visibility.

Examples include:

+--------+-----------------+
| unlock | subsequent lock |
+--------+-----------------+
+----------------+---------------+
| volatile write | subsequent vo |
+----------------+---------------+
+----------------+---------------+
| Thread.start() | actions in st |
+----------------+---------------+
+-----------------------+--------+
| all actions in thread | Thread |
+-----------------------+--------+

You don't need to memorize every JMM rule immediately, but you should understand:

When can one thread reliably see another thread's changes?

22. ConcurrentHashMap

One of the most important Java collections for concurrent backend systems.

ConcurrentHashMap<String, Integer> map =
        new ConcurrentHashMap<>();

Operations like:

put()
get()
remove()

are thread-safe.

But be careful with multi-step operations.

Instead of:

if (!map.containsKey(key)) {
    map.put(key, value);
}

use:

map.putIfAbsent(key, value);

23. computeIfAbsent

Extremely useful for rate limiters.

ConcurrentHashMap<String, Counter> counters =
        new ConcurrentHashMap<>();

Then:

Counter counter =
    counters.computeIfAbsent(
        userId,
        id -> new Counter()
    );

This allows lazy creation of per-user state.

25. Semaphore

A semaphore controls the number of concurrent permits.

Example:

Semaphore semaphore = new Semaphore(10);

Then:

semaphore.acquire();

try {
    performOperation();
} finally {
    semaphore.release();
}

Meaning:

Maximum 10 concurrent operations

This is different from a rate limiter.

Concurrency limiter

Controls:

How many operations can happen simultaneously?

Rate limiter

Controls:

How many operations can happen during a time period?

Example:

Concurrency limit:
10 requests simultaneously

Rate limit:
100 requests / second

Know this distinction very well.

34. Backpressure

Suppose requests arrive faster than your system can process them.

Incoming:
████████████████████████

Processing:
██████

Without protection:

+-------+     +------------------+     +-----+
| queue | --> | memory explosion | --> | sys |
+-------+     +------------------+     +-----+

With bounded queues:

+--------------------------------+
|           queue full           |
+--------------------------------+
                 |
                 v
+--------------------------------+
| block / reject / slow producer |
+--------------------------------+

This is backpressure.

Rate limiting is one mechanism for protecting a system from overload.

35. Deadlock

Four conditions commonly associated with deadlock:

  1. Mutual exclusion
  2. Hold and wait
  3. No preemption
  4. Circular wait

Example:

Thread A:
lock(A)
lock(B)

Thread B:
lock(B)
lock(A)

Result:

A waits for B
B waits for A

Deadlock.

36. Preventing deadlocks

Use consistent lock ordering.

Always:

lock A
then lock B

never:

+-------------+---+
| sometimes A | B |
+-------------+---+
+-------------+---+
| sometimes B | A |
+-------------+---+

Other techniques:

tryLock()

timeouts and minimizing lock scope.

37. Starvation

A thread never gets enough access to resources because other threads continuously take them.

Example:

+--------------------------------+
|       Thread A  waiting        |
+--------------------------------+
                 |
                 v
+--------------------------------+
| Thread B  repeatedly gets lock |
+--------------------------------+
                 |
                 v
+--------------------------------+
| Thread C  repeatedly gets lock |
+--------------------------------+

Thread A starves.

38. Livelock

Threads are active but make no progress.

Example:

Person A avoids Person B
Person B avoids Person A

Both keep changing behavior but nobody progresses.

39. Lock contention

If 100 threads compete for one lock:

+--------------------+
|        lock        |
+--------------------+
           |
           v
+--------------------+
|  ▼      ▼      ▼   |
+--------------------+
           |
           v
+--------------------+
| T1     T2 ... T100 |
+--------------------+

Only one can enter the critical section.

This can severely reduce throughput.

The goal isn't:

"Use fewer locks."

The goal is:

Protect correctness while minimizing unnecessary contention.

43. Lock-free vs wait-free

You should understand the terminology.

Lock-based

+------------------+
|       lock       |
+------------------+
          |
          v
+------------------+
| critical section |
+------------------+
          |
          v
+------------------+
|      unlock      |
+------------------+

Lock-free

System as a whole keeps making progress without traditional locks.

Often implemented using CAS.

Wait-free

Every individual operation is guaranteed to finish within a bounded number of steps.

Wait-free is stronger than lock-free.

47. Fixed Window algorithm

Simplest implementation.

Example:

100 requests / minute

Maintain:

windowStart
count

For each request:

if currentTime < windowEnd
    count++
else
    reset window

Example:

+--------------------+
| 12:00:00  12:00:59 |
+--------------------+
           |
           v
+--------------------+
|    100 requests    |
+--------------------+

Then reset:

12:01:00

48. Fixed Window problem

Boundary burst.

Suppose:

limit = 100/min

User sends:

+----------+--------------+
| 12:00:59 | 100 requests |
+----------+--------------+
+----------+--------------+
| 12:01:00 | 100 requests |
+----------+--------------+

That's:

200 requests

within roughly one second.

Yet each individual window was valid.

This is the boundary burst problem.

49. Fixed Window implementation

Conceptually:

class FixedWindowRateLimiter {

    private final int limit;
    private final long windowSizeMillis;

    private final AtomicInteger count =
            new AtomicInteger();

    private final AtomicLong windowStart =
            new AtomicLong();

    boolean allow() {
        // determine current window
        // reset if necessary
        // increment atomically
        // return whether request is allowed
    }
}

But don't stop here.

The hard part is making the window reset + increment atomic under concurrency.

50. Race condition in naive limiter

Bad:

if (count.get() < limit) {
    count.incrementAndGet();
    return true;
}
return false;

Two threads can both see:

count = 99
limit = 100

Both pass the check.

Then:

+----+-----+
| 99 | 100 |
+----+-----+
+-----+-----+
| 100 | 101 |
+-----+-----+

You allowed 101.

This is why concurrency knowledge matters.

51. Atomic check-and-update

You need a single logical operation:

check current state
        +
update state

must happen atomically.

Possible approaches:

ReentrantLock

The right choice depends on throughput and complexity.

52. Sliding Window

Instead of fixed windows:

12:00:00 → 12:00:59

track requests across the actual rolling interval.

For example:

current time = 12:00:40

look back:
11:59:40 → 12:00:40

Count requests in that interval.

53. Sliding Window Log

Store request timestamps:

+-------------+
|    [user]   |
+-------------+
       |
       v
+-------------+
| timestamps: |
+-------------+
       |
       v
+-------------+
|     10.1    |
+-------------+
       |
       v
+-------------+
|     10.2    |
+-------------+
       |
       v
+-------------+
|     10.5    |
+-------------+
       |
       v
+-------------+
|     10.8    |
+-------------+
       |
       v
+-------------+
|     ...     |
+-------------+

On each request:

  1. Remove timestamps older than the window.
  2. Count remaining timestamps.
  3. If count < limit, add current timestamp.
  4. Otherwise reject.

54. Sliding Window Log problem

Memory.

If:

1 million requests

you may store:

1 million timestamps

per large client/window.

So it can be expensive.

55. Sliding Window Counter

More memory efficient.

Use smaller fixed buckets:

10:00:00-10:00:09
10:00:10-10:00:19
10:00:20-10:00:29
...

Then estimate the rolling count using neighboring buckets.

This is a useful middle ground.

56. Token Bucket

This is one of the most important algorithms.

Imagine a bucket:

+-------------+
|    tokens   |
+-------------+
       |
       v
+-------------+
| ┌─────────┐ |
+-------------+
       |
       v
+-------------+
| │ ● ● ● ● │ |
+-------------+
       |
       v
+-------------+
| │ ● ● ●   │ |
+-------------+
       |
       v
+-------------+
| └─────────┘ |
+-------------+

Parameters:

capacity = 100
refillRate = 10 tokens/sec

Each request consumes:

1 token

If no token exists:

reject

57. Token bucket allows bursts

Suppose:

capacity = 100
refill = 10/sec

Bucket can accumulate 100 tokens.

A client can therefore send:

100 requests immediately

if tokens have accumulated.

Then it is limited to approximately:

10 requests/sec

as tokens refill.

This makes token bucket useful for APIs where controlled bursts are acceptable.

58. Token bucket formula

Suppose:

currentTokens
lastRefillTime
refillRate
capacity

Elapsed time:

elapsed = now - lastRefillTime

Tokens added:

elapsed × refillRate

Then:

newTokens =
    min(capacity,
        currentTokens + elapsed * refillRate)

Then request:

if newTokens >= 1:
    newTokens -= 1
    ALLOW
else:
    REJECT

59. Token bucket concurrency problem

Again:

Thread A reads 1 token
Thread B reads 1 token

Both might consume it.

Therefore:

read
calculate
update

must be atomic.

Possible solution:

ReentrantLock

or an atomic CAS-based state.

60. Token Bucket Java design

A good interview-level design:

class TokenBucket {

    private final long capacity;
    private final double refillRate;

    private long lastRefillNanos;

        try {
            refill();

            if (tokens >= 1) {
                tokens--;
                return true;
            }

            return false;
        } finally {
            lock.unlock();
        }
    }

}

Keep the critical section tiny.

61. Why use System.nanoTime()?

For elapsed-duration calculations, prefer:

rather than:

because nanoTime() is intended for measuring elapsed time and isn't affected in the same way by wall-clock adjustments.

Use wall-clock time when you need an actual timestamp.

96. Common mistakes

Mistake 1

Using:

HashMap

from multiple threads.

Use:

ConcurrentHashMap

or proper synchronization.

Mistake 2

Thinking volatile makes:

count++

safe.

It doesn't.

Mistake 3

Doing:

if (count < limit)
    count++;

without atomicity.

Mistake 4

Using one global lock for everything.

This can create severe contention.

Mistake 5

Creating unlimited threads.

Mistake 6

Using unbounded queues without understanding the memory implications.

Mistake 7

Calling:

Future.get()

without a timeout.

Mistake 8

Creating one local rate limiter per application server and assuming it is globally enforced.

Mistake 9

Ignoring cleanup of per-user state.

Mistake 10

Using currentTimeMillis() blindly for elapsed-time calculations.
