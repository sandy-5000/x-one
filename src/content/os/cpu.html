CPU registers, calling conventions, and context switching

The key to implementing a user-level threading library is understanding one fundamental idea:

A thread is not just a stack. It is a saved execution state that can be restored so the CPU continues executing as if the thread had never been paused.

When a C function calls another function, the compiler follows an ABI (Application Binary Interface) to decide where arguments go, which registers must survive the call, how the stack is organized, and how control returns. Your threading library must respect those rules when it switches between execution contexts.

This guide progresses from CPU registers to calling conventions, stack frames, assembly, and finally a minimal context-switching implementation for Apple Silicon and Linux.

1. The four layers you must distinguish

1. CPU architecture — AArch64 or x86-64

Defines the registers, instructions, address sizes, and how the processor executes instructions.

2. Operating system — macOS or Linux

Defines process and thread APIs, virtual memory, signals, system calls, and executable formats.

3. Compiler — Clang or GCC

Translates C into machine instructions and chooses which registers and stack locations hold variables.

4. ABI — the binary interface contract

Defines how separately compiled functions communicate: arguments, return values, preserved registers, stack alignment, and more.

For the platforms in this guide, the combinations are:

+---------------------------+--------------+----------------------------------------------------------------+
| Platform                  | Architecture | Main calling convention                                        |
+---------------------------+--------------+----------------------------------------------------------------+
| Apple Silicon macOS       | AArch64      | Apple ARM64 ABI, based on AAPCS64 with platform-specific rules |
| Linux on Intel/AMD 64-bit | x86-64       | System V AMD64 ABI                                             |
| Linux on ARM64            | AArch64      | AAPCS64, with applicable Linux platform rules                  |
+---------------------------+--------------+----------------------------------------------------------------+

Apple Silicon uses ARM64/AArch64, not x86-64. Intel Macs use x86-64. Linux can run on either architecture, among many others.

2. CPU registers: the processor's working storage

Registers are small, extremely fast storage locations inside the CPU. Most arithmetic, pointer manipulation, argument passing, and control flow use them directly.

Imagine this C code:

int add(int a, int b)
{
    return a + b;
}

Conceptually, the processor needs to:

  1. Obtain a.
  2. Obtain b.
  3. Add them.
  4. Put the result somewhere the caller can retrieve.

The ABI tells the caller and callee where those values should be. The exact registers depend on the architecture and calling convention.

2.1 Main categories of registers

Data

General-purpose registers (GPRs)

Hold integers, pointers, counters, arithmetic results, and temporary values.

Stack

Stack pointer (SP/RSP)

Identifies the current stack position. The ABI defines alignment and valid stack usage.

Frame

Frame pointer (FP/RBP)

Can provide a stable reference to a function's stack frame. It is often optional.

Control

Program counter (PC/RIP)

Identifies the instruction being executed or the next instruction according to the architecture's execution model.

Return

Link register (LR) or saved return address

Records where execution should continue after a function call.

Other register groups include floating-point/SIMD registers, condition flags, and architecture-specific control registers. A normal user-level context switch generally needs to preserve the ABI-required integer state and stack position, plus any additional state required by the chosen suspension model.

2.2 Apple Silicon / AArch64 register layout

AArch64 has 31 general-purpose registers, conventionally named x0 through x30. Each x register is 64 bits wide.

AArch64 integer registers

x0–x7

Arguments and results

x8

Indirect result / syscall use on Linux

x9–x15

Temporary registers

x16–x17

Intra-procedure scratch

x18

Platform register / platform-specific

x19–x28

Callee-saved

x29

FP: frame pointer by convention

x30

LR: link register

sp

Stack pointer

This is a practical ABI-oriented grouping. The exact role of some registers depends on the platform and instruction sequence.

What are xN and wN?

The x and w names refer to the same physical register, viewed at different widths.

64-bit view                    32-bit view
+-------------------------+    +-------------+
|          x0             |    |     w0      |
+-------------------------+    +-------------+
63                        0    31            0

For example:

mov     x0, #42       // x0 = 42
mov     w1, #7        // w1 = 7; upper 32 bits of x1 become zero
add     w0, w0, w1    // 32-bit addition; result in w0

A write to w0 zeroes the upper 32 bits of x0. This is an important distinction from some other register-width operations.

The special aliases

  • sp: stack pointer, with architectural rules governing its use.
  • x29 / fp: commonly used as the frame pointer.
  • x30 / lr: link register, commonly holds a function's return address.
  • pc: the program counter, not a normal general-purpose register that can be freely accessed like x0.
  • xzr / wzr: zero-register aliases that read as zero and discard writes.

AArch64 also has v0–v31 SIMD/floating-point registers, with views such as d0 and q0. They matter when a function passes floating-point values or when a context switch must preserve a broader execution state.

Why x18 deserves special care

On Linux AArch64, x18 is generally treated as a platform register or otherwise reserved according to the platform ABI. Apple also reserves it for platform-specific use. Do not treat it as an ordinary scratch register in portable assembly.

2.3 Linux x86-64 register layout

x86-64 uses 64-bit general-purpose registers with historically inherited names.

x86-64 general-purpose registers

rax

Return value; arithmetic

rbx

Callee-saved

rcx

Argument 4; scratch

rdx

Argument 3; scratch

rsi

Argument 2

rdi

Argument 1

rbp

Optional frame pointer

rsp

Stack pointer

rip

Instruction pointer

r8–r9

Arguments 5–6

r10–r11

Caller-saved scratch

r12–r15

Callee-saved

The register names have smaller-width aliases. For example:

rax (64-bit)
+------------------------------------------------+
|                    rax                         |
+------------------------------------------------+
                               eax (low 32 bits)
                               ax  (low 16 bits)
                               al  (low 8 bits)
                               ah  (bits 8–15)

Writing to a 32-bit register such as eax zeroes the upper 32 bits of rax in 64-bit mode. Writing to ax or al does not generally zero the rest of the register.

For example:

mov     rax, 0x1122334455667788
mov     eax, 42

After the second instruction, rax is 42, not 0x112233440000002a.

Unlike AArch64, x86-64 has a directly visible rip register in debugger output, but ordinary instructions cannot freely write arbitrary values to it. Control-transfer instructions change the instruction pointer.

3. Calling conventions: how C functions communicate

A calling convention is a contract between caller and callee. It determines:

  • Which registers carry arguments.
  • Where excess arguments go.
  • Where return values appear.
  • Which registers the callee must preserve.
  • How the stack must be aligned.
  • How control returns to the caller.

Consider:

long sum(long a, long b, long c)
{
    return a + b + c;
}

int main(void)
{
    return (int)sum(10, 20, 30);
}

The compiler does not need to place every variable on the stack. It can pass arguments and calculate the result entirely in registers.

3.1 Linux x86-64: System V AMD64 ABI

For ordinary integer and pointer arguments, the first six are passed in:

+----------+--------------------------------+
| Argument | Register                       |
+----------+--------------------------------+
| 1        | `rdi`                          |
| 2        | `rsi`                          |
| 3        | `rdx`                          |
| 4        | `rcx`                          |
| 5        | `r8`                           |
| 6        | `r9`                           |
| 7 onward | Stack, according to ABI layout |
+----------+--------------------------------+

Integer and pointer return values normally use rax; certain wider results use additional registers, and floating-point values normally use xmm0 and related SIMD registers.

A simplified call sequence could look like this:

mov     edi, 10
mov     esi, 20
mov     edx, 30
call    sum

The values are put in the argument registers before the call.

What does call do?

In x86-64, a near call:

  1. Pushes the return address onto the stack.
  2. Transfers execution to the target function.

If call sum is at address 0x1000 and the following instruction is at 0x1005, the return address is 0x1005.

Before call:
    rsp -> caller's current stack top

After call:
    rsp -> return address
           caller's previous stack contents

A typical ret pops the return address into the instruction pointer and continues execution there.

The return address is therefore stored on the stack by the hardware call mechanism, not in a dedicated x86-64 link register.

3.2 Linux ARM64: AAPCS64

For ordinary integer and pointer arguments:

+------------------------+----------------------------------------------------------------+
| Argument               | Register                                                       |
+------------------------+----------------------------------------------------------------+
| 1–8                    | `x0`–`x7`                                                      |
| Additional arguments   | Stack, according to ABI layout                                 |
| Integer/pointer result | Usually `x0` (and possibly `x1` for certain composite results) |
+------------------------+----------------------------------------------------------------+

Floating-point and SIMD arguments follow separate rules, commonly using v0–v7.

A simplified sequence:

mov     x0, #10
mov     x1, #20
mov     x2, #30
bl      sum

What does bl do?

bl means branch with link:

  1. Stores the return address in x30 (lr).
  2. Branches to the target function.

Unlike x86-64 call, bl does not push the return address onto the stack automatically.

Before bl:
    x30 = previous link-register value

After bl:
    x30 = address of instruction following bl
    PC  = target function

A function that needs to make another call must preserve its own return address if that next call will overwrite x30. This is one reason ARM64 functions often save lr to the stack.

3.3 Apple Silicon macOS: the Apple ARM64 ABI

Apple Silicon uses the AArch64 instruction set and follows an ARM64 ABI derived from AAPCS64, with Apple-specific rules.

For ordinary integer and pointer calls, you can generally expect:

  • x0–x7 for arguments.
  • x0 for a simple integer/pointer return value.
  • x19–x28 to be preserved by the callee.
  • x29 commonly used as the frame pointer.
  • x30 used as the link register.
  • sp to obey the required stack alignment.

However, do not assume every Linux ARM64 ABI detail is identical on macOS. Platform-specific register use, stack rules, symbol naming, unwind metadata, and security features can matter. For assembly intended to run on Apple platforms, consult Apple's ARM64 ABI documentation and inspect compiler-generated output for the target.

3.4 One function, three calling conventions

Suppose you call:

long multiply_add(long a, long b, long c)
{
    return a * b + c;
}

The conceptual argument mapping is:

Linux x86-64

rdi = a

rsi = b

rdx = c

Return in rax.

Linux ARM64

x0 = a

x1 = b

x2 = c

Return in x0.

Apple Silicon macOS

x0 = a

x1 = b

x2 = c

Return in x0 for this simple integer result.

The source code is identical. The ABI and target architecture determine the machine-level interface.

4. Caller-saved vs. callee-saved registers

This distinction is the most important ABI concept for implementing a context switch.

A function call can overwrite many registers. The ABI defines which registers a function must preserve and which registers its caller must assume may be destroyed.

4.1 Caller-saved registers

Also called volatile registers.

The caller must save any value it still needs after a call if that value is in a caller-saved register.

Example:

long calculate(long a)
{
    long temporary = a * 2;

    helper();

    return temporary + a;
}

If the compiler keeps temporary in a caller-saved register, it must preserve that value across helper()—perhaps by moving it to a callee-saved register or spilling it to the stack.

The helper() function is allowed to overwrite caller-saved registers.

4.2 Callee-saved registers

Also called nonvolatile registers.

If the callee uses one of these registers, it must restore its incoming value before returning.

For example:

// Pseudocode illustrating the contract
save callee_saved_register
modify callee_saved_register
restore callee_saved_register
return

The caller does not need to save these registers merely because it is making an ordinary function call.

4.3 Register preservation tables

Linux x86-64 — System V AMD64

+--------------+------------------------------------------------------------------+
| Register     | Classification                                                   |
+--------------+------------------------------------------------------------------+
| `rax`        | Caller-saved                                                     |
| `rcx`, `rdx` | Caller-saved                                                     |
| `rsi`, `rdi` | Caller-saved                                                     |
| `r8`–`r11`   | Caller-saved                                                     |
| `rbx`        | Callee-saved                                                     |
| `rbp`        | Callee-saved                                                     |
| `r12`–`r15`  | Callee-saved                                                     |
| `rsp`        | Must be restored to the appropriate stack position before return |
| `rip`        | Control-flow state, not an ordinary preserved GPR                |
+--------------+------------------------------------------------------------------+

The caller-saved list is also important when calling functions through pointers, because the callee can be any compatible function.

Linux ARM64 and Apple Silicon

+-------------+------------------------------------------------------------------------------------------+
| Register    | Classification                                                                           |
+-------------+------------------------------------------------------------------------------------------+
| `x0`–`x7`   | Caller-saved; argument/result registers                                                  |
| `x8`        | Caller-saved; special indirect-result use in the standard ABI                            |
| `x9`–`x15`  | Caller-saved                                                                             |
| `x16`–`x17` | Caller-saved scratch registers; may be used by linkage sequences                         |
| `x18`       | Platform-specific; do not use as portable scratch storage                                |
| `x19`–`x28` | Callee-saved                                                                             |
| `x29`       | Callee-saved; commonly the frame pointer                                                 |
| `x30`       | Link register; must be saved when its incoming return address must survive a nested call |
| `sp`        | Must be restored to its required value and alignment                                     |
+-------------+------------------------------------------------------------------------------------------+

The SIMD/floating-point registers have their own preservation rules. In the standard AAPCS64 convention, v8–v15 have callee-preservation requirements for their low 64-bit portions; other SIMD register portions are generally caller-saved. Check the specific platform ABI when saving a complete machine context.

4.4 Why this matters for a context switch

Imagine thread A is executing:

long x = 100;
long y = 200;

yield();

use(x, y);

Before yield(), the compiler might place x in rbx and y in r12. Or it might place them in volatile registers and save them elsewhere. It may even recompute them after the call.

Because yield() is an ordinary C function call, the compiler already assumes that caller-saved registers can be overwritten. It expects callee-saved registers to survive.

Therefore, a minimal cooperative context switch can preserve the ABI's callee-saved registers and stack pointer, rather than blindly copying every general-purpose register.

Important distinction: this is enough for switching between contexts that yield through the normal function-call interface. It is not automatically enough for an asynchronous preemptive switch that can interrupt arbitrary instructions.

5. How C variables map to registers and memory

C defines variables and their observable behavior, not their physical register assignments.

Consider:

long add(long a, long b)
{
    long result = a + b;
    return result;
}

At optimization level -O0, a compiler may use a stack frame and store values in memory. At -O2, it may never allocate a stack slot for result.

5.1 Possible mapping on Linux x86-64

An optimized implementation might be:

add:
    lea     rax, [rdi + rsi]
    ret

Interpretation:

  • rdi contains a.
  • rsi contains b.
  • lea calculates the effective address expression rdi + rsi; here, it is used as arithmetic rather than to load memory.
  • rax contains the return value.
  • ret returns to the caller.

No local variable needs to exist in memory.

5.2 Possible mapping on AArch64

add:
    add     x0, x0, x1
    ret

Interpretation:

  • x0 initially contains a.
  • x1 contains b.
  • add computes the sum in x0.
  • ret normally branches to the address in x30.

The input register is reused for the output, so the compiler doesn't need a separate register for result.

5.3 Pointers and dereferencing

Consider:

long read_value(const long *ptr)
{
    return *ptr;
}

On x86-64, an implementation may use:

mov     rax, QWORD PTR [rdi]
ret

Here, rdi contains the pointer, and [rdi] means the memory addressed by that pointer.

On AArch64:

ldr     x0, [x0]
ret

ldr loads the 64-bit value at the address in x0, replacing the pointer with the result.

This is the central difference between a register containing an address and the memory at that address:

x0 = 0x1000                 Memory
                            Address    Value
                            0x1000     1234
    ldr x0, [x0]             x0 = 1234

5.4 Why a local variable may not appear in a debugger

The compiler can:

  • Keep a variable in a register.
  • Reuse a register for different variables at different times.
  • Store a variable in a stack slot.
  • Eliminate a variable entirely.
  • Constant-fold an expression.
  • Recompute a value instead of saving it.

For example:

int square_plus_one(int x)
{
    int square = x * x;
    return square + 1;
}

At optimization levels such as -O2, the compiler can keep everything in registers and emit only the instructions needed for the result.

Debugging with -O0 -g usually makes the source-to-machine mapping easier to follow. Optimization can produce variables that are reported as “optimized out”; that does not mean the program is necessarily incorrect.

6. Stack frames and stack memory

A stack frame is the portion of stack memory associated with a function invocation. It may hold saved registers, local variables, spilled temporaries, outgoing arguments, and other bookkeeping.

Most mainstream ABIs use a stack that grows toward lower memory addresses. This means allocating more stack space usually decreases the stack pointer.

6.1 Stack growth

Higher memory addresses
        |
        v
+-----------------------------+
| Caller stack data           |
+-----------------------------+
| Return address / saved data |
+-----------------------------+
| Local variables             |
+-----------------------------+  <- current SP
        ^
        |
  Stack grows downward
  toward lower addresses

Lower memory addresses

This is a conceptual diagram. The exact arrangement depends on the architecture, ABI, compiler, and optimization settings.

x86-64 example

A function might begin:

push    rbp
mov     rbp, rsp
sub     rsp, 32

Instruction by instruction:

  1. push rbp saves the caller's frame-pointer value on the stack.
  2. mov rbp, rsp establishes the new frame pointer.
  3. sub rsp, 32 reserves 32 bytes for local storage or temporary use.

This is a common prologue, not a requirement for every function.

A corresponding epilogue might be:

mov     rsp, rbp
pop     rbp
ret

It restores the stack pointer, restores the old frame pointer, and returns.

6.2 AArch64 example

A function that calls another function and uses the frame pointer might begin:

stp     x29, x30, [sp, #-16]!
mov     x29, sp

Here:

  • stp stores two 64-bit registers.
  • x29 is the old frame pointer.
  • x30 is the incoming link register.
  • [sp, #-16]! decrements sp by 16 first, then stores the pair at the new address.
  • mov x29, sp establishes the frame pointer.

The epilogue can be:

ldp     x29, x30, [sp], #16
ret

ldp restores both registers, then increments sp by 16. ret branches to the return address in x30, unless a different register is explicitly specified.

The save is essential when the function makes a nested call that overwrites x30, because the original caller's return address must survive.

6.3 Stack alignment

Alignment is an ABI requirement, not just a performance optimization.

  • On System V AMD64, the stack is normally 16-byte aligned at the call boundary in the ABI-defined way; at entry to an ordinary function, the pushed return address means rsp is typically 8 modulo 16.
  • On AArch64, sp must obey 16-byte alignment at public interfaces and under the architecture's stack-pointer rules.

Misaligned stack usage can cause crashes, incorrect behavior, or ABI violations, especially when using SIMD instructions or calling library functions.

A context switch must restore a valid stack pointer for the target context. If it begins executing ordinary C code with a misaligned stack, even seemingly unrelated C calls can fail.

7. Assembly instructions you need to know

The same idea often has different instructions on different architectures.

+-------------------------+------------------------------------------+------------------------------------------------------------+
| Purpose                 | x86-64                                   | AArch64                                                    |
+-------------------------+------------------------------------------+------------------------------------------------------------+
| Move register/immediate | `mov`                                    | `mov` (often an alias for another instruction)             |
| Load memory             | `mov reg, [addr]`                        | `ldr`                                                      |
| Store memory            | `mov [addr], reg`                        | `str`                                                      |
| Push a register         | `push`                                   | No general-purpose `push`; adjust `sp` and use `str`/`stp` |
| Pop a register          | `pop`                                    | No general-purpose `pop`; use `ldr`/`ldp` and adjust `sp`  |
| Store/load a pair       | Multiple instructions or memory operands | `stp` / `ldp`                                              |
| Call a function         | `call`                                   | `bl`                                                       |
| Return                  | `ret`                                    | `ret`                                                      |
| Indirect branch         | `jmp reg`                                | `br xN`                                                    |
| Indirect return         | `ret`                                    | `ret`                                                      |
+-------------------------+------------------------------------------+------------------------------------------------------------+

7.1 mov

x86-64:

mov     rax, rdi
mov     rax, 42

AArch64:

mov     x0, x1
mov     x0, #42

mov copies a value or materializes an immediate using the instruction forms permitted by the architecture. On AArch64, assemblers may translate mov into an alias such as orr or a sequence of instructions depending on the immediate.

7.2 push and pop

x86-64:

push    rbx
pop     rbx

push rbx decrements rsp by 8 and stores rbx there. pop rbx loads the top stack value and increments rsp by 8.

AArch64 has no general-purpose push or pop instructions. The usual equivalent is:

str     x19, [sp, #-16]!
ldr     x19, [sp], #16

The store reserves 16 bytes but uses only 8 bytes for x19; the extra space keeps the stack aligned. Paired saves are usually more natural:

stp     x19, x20, [sp, #-16]!
ldp     x19, x20, [sp], #16

7.3 ldr and str

ldr     x0, [x1]       // x0 = 64-bit value at address x1
str     x0, [x1]       // store x0 at address x1

The brackets indicate memory access. The exact transfer size depends on the register and instruction form.

7.4 stp and ldp

stp     x19, x20, [sp, #-16]!
ldp     x19, x20, [sp], #16

These efficiently save and restore two registers. The ! denotes pre-indexed addressing: update the base register before accessing memory. The trailing offset on ldp is post-indexed: access memory first, then update the base register.

7.5 call, ret, bl, and br

On x86-64:

call    function
ret
jmp     rax
  • call saves a return address on the stack and branches.
  • ret consumes the return address from the stack.
  • jmp rax transfers control to the address in rax without creating a new return address.

On AArch64:

bl      function
ret
br      x9
  • bl writes the return address to x30, then branches.
  • ret normally branches to x30.
  • br x9 branches to the address in x9 without setting a new link register.

For a context switch, the distinction between a call and a branch is crucial. A call creates a return path. A branch transfers control directly. You must choose based on how the saved context is laid out and where the resumed execution is expected to continue.

8. Context switching: saving and restoring execution state

A user-level threading library runs multiple logical threads inside one operating-system thread. It does not need the kernel to schedule every logical thread: your library decides when to pause one and resume another.

8.1 What state does a thread need?

A minimal cooperative thread context typically needs:

  • Its stack pointer.
  • Its callee-saved registers.
  • A way to resume at the point immediately after the previous yield() call.

The stack itself contains the suspended function calls' local state, return addresses, and any saved registers the compiler placed there.

Conceptually:

Thread A paused, Thread B resumed

Thread A context

Saved stack pointer

SP-A

Saved callee-saved registers + Thread A's existing stack frames

Context switch routine

Thread B context

Restored stack pointer

SP-B

Restored callee-saved registers + Thread B's own stack frames

A context switch does not normally copy the whole stack. It saves the location of the stack and restores the saved registers that the ABI requires to survive the switch.

8.2 Why switching at a function-call boundary is simpler

Suppose the C function yield() calls an assembly routine named context_switch.

void yield(void)
{
    context_switch(&current->context, &next->context);
}

When the assembly routine saves its caller's stack pointer and callee-saved registers, it captures a state consistent with an ordinary function call. When that context is restored, the assembly routine returns to the old caller, and yield() continues.

The compiler has already made sure that values it needs after context_switch() survive according to the ABI. The context-switch routine must preserve the callee-saved registers exactly as a normal function would.

This is why cooperative context switching is substantially simpler than interrupting arbitrary instructions.

8.3 Linux x86-64: educational context-switch assembly

Define the saved context as a stack pointer:

typedef struct
{
    void *sp;
} Context;

extern void context_switch(Context *old_context,
                           Context *new_context);

The assembly below uses GNU assembler's AT&T syntax, which is commonly used by GCC and Clang on Linux.

    .text
    .globl context_switch
    .type context_switch, @function

context_switch:
    pushq   %rbx
    pushq   %rbp
    pushq   %r12
    pushq   %r13
    pushq   %r14
    pushq   %r15

    movq    %rsp, (%rdi)       # old_context->sp = rsp
    movq    (%rsi), %rsp       # rsp = new_context->sp

    popq    %r15
    popq    %r14
    popq    %r13
    popq    %r12
    popq    %rbp
    popq    %rbx

    ret

Instruction-by-instruction trace

  1. pushq %rbx through pushq %r15 preserve all six callee-saved GPRs required by this implementation.
  2. %rdi contains old_context, and (%rdi) is the memory location of its sp field.
  3. movq %rsp, (%rdi) saves the current stack pointer.
  4. %rsi contains new_context; movq (%rsi), %rsp installs its saved stack pointer.
  5. The popq instructions restore the new context's saved registers in reverse stack order.
  6. ret consumes the return address at the top of the restored stack.

For a previously suspended thread, that return address takes execution back into the earlier invocation of context_switch. That invocation returns to the C code following its call.

The register argument values %rdi and %rsi do not need to survive the switch because they are caller-saved under System V AMD64.

8.4 Linux ARM64 and Apple Silicon: educational context-switch assembly

The equivalent AArch64 version saves the callee-saved registers in pairs. It uses the same Context structure, with the appropriate pointer type.

    .text
    .globl context_switch
    .type context_switch, %function

context_switch:
    stp     x19, x20, [sp, #-16]!
    stp     x21, x22, [sp, #-16]!
    stp     x23, x24, [sp, #-16]!
    stp     x25, x26, [sp, #-16]!
    stp     x27, x28, [sp, #-16]!
    stp     x29, x30, [sp, #-16]!

    str     sp, [x0]            // old_context->sp = sp
    ldr     x9, [x1]            // x9 = new_context->sp
    mov     sp, x9              // switch stack

    ldp     x29, x30, [sp], #16
    ldp     x27, x28, [sp], #16
    ldp     x25, x26, [sp], #16
    ldp     x23, x24, [sp], #16
    ldp     x21, x22, [sp], #16
    ldp     x19, x20, [sp], #16

    ret

Why these instructions are needed

  • Each stp saves two 64-bit registers and decrements sp by 16 bytes.
  • str sp, [x0] records the old context's stack pointer through the pointer in x0.
  • ldr x9, [x1] reads the new stack pointer. x9 is caller-saved and can be used as a temporary.
  • mov sp, x9 transfers execution to the other stack.
  • ldp restores the register pairs in reverse order and advances sp.
  • ret branches to the restored x30.

The routine preserves x19–x30, including x29 and x30. Preserving x30 matters because the saved context must return to the correct suspended call site.

This minimal example is designed for ordinary cooperative switches, not asynchronous preemption. It also assumes a valid context pointer, a correctly initialized stack, and ABI-compliant stack alignment.

9. Initializing a new thread's stack

A newly allocated stack does not automatically contain a valid function call frame. You must construct an initial stack layout that matches what the assembly restore routine expects.

There are two common designs:

  1. Restore a fabricated register context and return into a startup trampoline.
  2. Restore a context and jump directly to an entry function, with a carefully designed ABI-compliant setup.

A startup trampoline is useful because it can call a normal C function and handle the function's return.

9.1 Thread entry interface

For example:

typedef void (*ThreadFunction)(void *);

typedef struct
{
    void *sp;
} Context;

typedef struct
{
    Context context;
    ThreadFunction function;
    void *argument;
    void *stack;
    size_t stack_size;
} Thread;

A trampoline can call the thread function and then terminate the logical thread:

extern void thread_exit(void);

static void thread_bootstrap(ThreadFunction function,
                             void *argument)
{
    function(argument);
    thread_exit();

    __builtin_unreachable();
}

The precise assembly interface for the trampoline depends on how the initial context stores function and argument. Do not assume that the values in caller-saved registers from the moment of allocation will still be available after the context is restored.

9.2 Initial stack layout on x86-64

For the x86-64 switch routine above, the restore sequence expects this layout at the saved stack pointer:

Lower memory addresses
        |
        v
+---------------------------+  <- saved context.sp
| r15                       |
+---------------------------+
| r14                       |
+---------------------------+
| r13                       |
+---------------------------+
| r12                       |
+---------------------------+
| rbp                       |
+---------------------------+
| rbx                       |
+---------------------------+
| return address            |  <- trampoline
+---------------------------+
| alignment padding         |
+---------------------------+
Higher memory addresses

The register slots must match the order of the popq instructions. The return address must point to executable code, not to a C object or an arbitrary stack location.

If the trampoline is entered through ret, the fabricated return address plays the role normally created by call. Its entry stack alignment must also match the ABI. In the standard x86-64 calling convention, a function reached through an ordinary call normally begins with %rsp % 16 == 8.

If the trampoline calls another C function, its own stack usage must maintain the required alignment before that call. The System V AMD64 red zone—128 bytes below %rsp—is another consideration: it is available to ordinary user-space functions under the ABI, so the stack must have sufficient valid space and must not overlap other data inappropriately.

9.3 Initial stack layout on AArch64

For the AArch64 restore routine above, the initial layout is:

Lower memory addresses
        |
        v
+---------------------------+  <- saved context.sp
| x29                       |
| x30 = trampoline address  |
+---------------------------+
| x27                       |
| x28                       |
+---------------------------+
| x25                       |
| x26                       |
+---------------------------+
| x23                       |
| x24                       |
+---------------------------+
| x21                       |
| x22                       |
+---------------------------+
| x19                       |
| x20                       |
+---------------------------+
Higher memory addresses

Each pair occupies 16 bytes. The initial sp should be 16-byte aligned.

The ret instruction uses the restored x30, so initialize it to the trampoline address. The other restored registers can carry startup state if the trampoline is explicitly designed to consume it—for example, x19 for the function pointer and x20 for its argument. Since these are callee-saved registers, an ordinary C trampoline must preserve their incoming values if it uses them and subsequently returns.

A robust implementation also considers stack guards, cleanup when the thread returns, error handling, and platform-specific control-flow protection. The diagrams show the register layout, not a complete production-ready thread runtime.

10. The complete execution trace

Assume Thread A executes:

void worker_a(void)
{
    int value = 42;

    yield();

    consume(value);
}

And Thread B has its own stack and execution state.

The sequence is:

  1. Thread A calls yield().The compiler emits a normal function call. The return address for yield() is created by the architecture's call mechanism.
  2. Thread A enters context_switch().The assembly saves the callee-saved registers and records the current stack pointer in A's context.
  3. The switch routine loads Thread B's saved stack pointer.All subsequent stack accesses refer to B's stack.
  4. Thread B's registers are restored.The saved registers are loaded in reverse order. ret transfers control to B's saved return address.
  5. Thread B resumes.If B previously yielded, execution resumes after its earlier call to context_switch(). If B is new, the fabricated return address leads to its startup trampoline.
  6. Later, Thread A is selected again.Its saved stack pointer and registers are restored. Its earlier context-switch call returns, yield() finishes, and consume(value) executes.

The value variable does not need to be explicitly saved by the context-switch assembly. If the compiler needs it after yield(), it must follow the calling convention. Its value may reside in a callee-saved register, a stack slot, or another valid representation.

11. Platform differences: macOS, Linux, Clang, and GCC

The assembly instructions can be identical across operating systems using the same architecture, while symbol names, object-file formats, ABI details, and linking conventions differ.

11.1 Symbol naming

C compilers typically expose C function names to the linker as symbols.

On Linux, a function named context_switch normally has the symbol:

context_switch

On macOS, C symbols conventionally have a leading underscore in the object file:

_context_switch

For example, an assembly function on macOS might begin:

.text
.globl _context_switch
.p2align 2

_context_switch:
    ret

On Linux AArch64, the equivalent symbol is normally:

.text
.globl context_switch
.type context_switch, %function

context_switch:
    ret

On Linux x86-64, use the corresponding GNU assembler function directive and symbol name. The leading underscore is a platform object-format convention, not an instruction-set difference.

11.2 .S versus .s

+-----------+-----------------------------------------------------+
| Extension | Behavior                                            |
+-----------+-----------------------------------------------------+
| `.s`      | Assembly source is passed directly to the assembler |
| `.S`      | Assembly source is preprocessed before assembly     |
+-----------+-----------------------------------------------------+

Use .S if you want conditional compilation:

#ifdef __APPLE__
    // macOS-specific symbols or directives
#else
    // Linux-specific symbols or directives
#endif

For example, the symbol name can be selected with a macro:

#ifdef __APPLE__
#define CONTEXT_SWITCH _context_switch
#else
#define CONTEXT_SWITCH context_switch
#endif

.globl CONTEXT_SWITCH
CONTEXT_SWITCH:
    ret

This illustrates preprocessing; a complete cross-platform assembly file may also need different directives and unwind metadata.

11.3 Clang versus GCC

Both Clang and GCC can compile C and assembly for supported targets. Their output can differ in register allocation, prologue/epilogue generation, instruction selection, optimization, and debug information.

On Apple Silicon, Clang is the standard compiler toolchain for macOS. GCC is commonly used on Linux; Clang is also widely available there.

Neither compiler guarantees that a source-level variable will occupy a particular register. The ABI constrains the interface, while the compiler decides how to implement the function internally.

11.4 Useful architecture checks

Run these commands to identify the environment:

uname -m
clang --version
gcc --version

Common architecture results:

  • arm64 on Apple Silicon macOS.
  • x86_64 on Intel/AMD 64-bit Linux.
  • aarch64 on Linux ARM64.

On macOS, you can also inspect the machine architecture of an executable:

file ./program
lipo -info ./program

The second command is useful for universal binaries containing multiple architectures.

12. Practical exercises

These exercises build from simple register operations to the context-switching library.

Exercise 1 — Compile a C function and inspect its assembly

Create add.c:

long add(long a, long b)
{
    return a + b;
}

int main(void)
{
    return (int)add(10, 20);
}

Compile without optimization:

clang -O0 -g -S add.c -o add-O0.s

Compile with optimization:

clang -O2 -g -S add.c -o add-O2.s

Compare the outputs.

Look for:

  • Where arguments arrive.
  • Whether a stack frame is created.
  • Whether add is inlined or optimized.
  • Whether the compiler emits a ret.
  • How much simpler the optimized function becomes.

On Linux, you can also use GCC:

gcc -O2 -g -S add.c -o add-gcc.s

Exercise 2 — Observe register arguments in a debugger

Compile:

clang -O0 -g add.c -o add
lldb ./add

Inside LLDB:

(lldb) breakpoint set --name add
(lldb) run
(lldb) register read
(lldb) disassemble --name add

On Linux, using GDB:

gcc -O0 -g add.c -o add
gdb ./add

Then:

(gdb) break add
(gdb) run
(gdb) info registers
(gdb) disassemble /m add

On x86-64, inspect rdi and rsi for the two integer arguments. On AArch64, inspect x0 and x1.

Note that an optimized build can inline the function or remove it from the final machine code. Use a low optimization level initially.

Exercise 3 — Write an assembly function called from C

This exercise teaches the C ABI without introducing stack switching.

Create main.c:

#include <stdio.h>

extern long asm_add(long a, long b);

int main(void)
{
    printf("%ld\n", asm_add(12, 30));
    return 0;
}

Linux x86-64: add.S

.text
.globl asm_add
.type asm_add, @function

asm_add:
    leaq    (%rdi, %rsi), %rax
    ret

Compile:

gcc main.c add.S -o add
./add

Expected output:

42

The first two arguments arrive in rdi and rsi. The result is returned in rax.

AArch64: add.S

.text
.globl asm_add
.type asm_add, %function

asm_add:
    add     x0, x0, x1
    ret

On Linux ARM64:

gcc main.c add.S -o add
./add

On Apple Silicon macOS, use this symbol name instead:

.text
.globl _asm_add
.p2align 2

_asm_add:
    add     x0, x0, x1
    ret

Compile with:

clang main.c add.S -o add
./add

Both versions return 42. The arithmetic is the same, but the instruction syntax and symbol naming differ.

Exercise 4 — Examine a function prologue and epilogue

Create frame.c:

extern void helper(long *);

long calculate(long a, long b)
{
    long values[4];

    values[0] = a;
    values[1] = b;
    values[2] = a + b;
    values[3] = a * b;

    helper(values);

    return values[2] + values[3];
}

Compile:

clang -O0 -g -S frame.c -o frame.s

Then:

clang -O0 -g frame.c -c -o frame.o
objdump -d frame.o

On macOS, use:

clang -O0 -g -c frame.c -o frame.o
llvm-objdump --disassemble frame.o

Observe:

  • The stack space reserved for values.
  • How the compiler accesses array elements.
  • Which registers hold a and b.
  • How the compiler preserves any values needed after helper().
  • Whether the compiler uses a frame pointer.

The precise assembly is compiler- and target-dependent. Focus on the ABI rules rather than memorizing a single listing.

Exercise 5 — Build the context switch incrementally

Implement these steps in order:

  1. Define Context with a saved stack pointer.
  2. Implement an assembly routine that saves and restores the callee-saved registers without switching stacks.
  3. Add two independently allocated stacks.
  4. Initialize one stack with a valid initial register layout and trampoline return address.
  5. Add a C yield() function that chooses another runnable context.
  6. Add thread completion and stack cleanup.
  7. Add tests that verify local variables survive repeated yields.

Test simple cases first:

void worker(void *arg)
{
    int id = *(int *)arg;

    for (int i = 0; i < 5; ++i)
    {
        printf("thread %d: iteration %d\n", id, i);
        yield();
    }
}

Do not assume the output will alternate strictly unless the scheduler deliberately implements round-robin scheduling. The test is meant to verify that each thread's state survives the switch.

Before relying on this code, test stack alignment, return behavior, repeated switching, and cleanup under both debug and optimized builds.

13. Important limitations of a minimal context switch

A cooperative context switch at a function-call boundary is a useful educational foundation, but it is not a complete implementation of every possible threading model.

+-------------------------------------+--------------------------------------------------------------------------------------------------------------+
| Concern                             | Why it matters                                                                                               |
+-------------------------------------+--------------------------------------------------------------------------------------------------------------+
| Floating-point/SIMD state           | Needed if your switching model requires preserving it beyond the ordinary ABI guarantees                     |
| `errno` and thread-local storage    | May be associated with the operating-system thread, not automatically with your user-level thread            |
| Signals and asynchronous preemption | Can interrupt code outside a normal call boundary                                                            |
| Stack guards                        | Detect stack overflow and prevent silent memory corruption                                                   |
| Unwind/debug metadata               | Needed for reliable backtraces, exceptions, and debugger support                                             |
| Sanitizers                          | AddressSanitizer and other tools need to be informed about fiber/stack switching where applicable            |
| Security features                   | Pointer authentication, control-flow protection, and shadow stacks can constrain fabricated return addresses |
| Thread termination                  | A thread must not return through an invalid or nonexistent caller frame                                      |
| Scheduler synchronization           | Concurrent access from multiple kernel threads requires additional synchronization                           |
+-------------------------------------+--------------------------------------------------------------------------------------------------------------+

In particular, a fabricated stack and return address should not be treated as universally portable. For a production implementation, platform-specific facilities such as supported fiber/context APIs may be preferable.

14. Recommended learning order

  1. Registers and instruction executionLearn mov, add, ldr, str, call, ret, bl, and br.
  2. Calling conventionsBe able to explain argument registers, return registers, and caller-saved versus callee-saved registers for each target.
  3. Stack framesWrite functions that save registers, allocate stack space, call another function, and restore state.
  4. C-to-assembly integrationCall assembly from C and call C from assembly. Inspect the generated code.
  5. Cooperative context switchingSave the ABI-preserved state and stack pointer, then restore another context.
  6. Thread initialization and schedulingConstruct a valid initial context, implement a trampoline, and manage thread completion.

The central rule to retain is this: the architecture defines what the CPU can do; the ABI defines what functions must agree to do; the compiler decides how C code uses those facilities. A correct user-level threading library must respect all three.
